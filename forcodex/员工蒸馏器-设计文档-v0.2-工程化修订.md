# 员工蒸馏器 · 设计文档 v0.2（工程化修订）

> 基于 `员工蒸馏器-设计文档.md` 的新版本整理。
> 这份文档不替换原稿，目标是把原方案从“产品设计稿”推进到“更接近可实现规格”。
> 日期：2026-06-20

---

## 0. 这版修了什么

v0.1 的方向是对的，但有几个地方对工程现实过于乐观。这一版重点修正 6 件事：

1. 不再把“跑通”近似当成“语义正确”
2. 不再把 AST/静态扫描写成可以可靠证明纯度和确定性
3. 给统一 trace schema 补足复现、合并、回退所需字段
4. 把 MCP 的角色收敛为“统一执行层”，不再泛化成“统一原生体验”
5. 给入库增加两条晋升路径，避免 `N >= 3` 错杀高价值低频能力
6. 进一步缩小 MVP 范围，保证数周内真的能跑通

---

## 1. 一句话定义

员工蒸馏器是一个针对程序类能力的运行时沉淀系统：它从 agent 的真实执行轨迹中发现候选工具，经过复现、验证、归一、合并后，沉淀为可检索、可回放、可复用的能力资产，并通过 MCP 和宿主适配层重新提供给后续任务使用。

---

## 2. 核心边界

### 2.1 本期纳入范围

- 可执行工具
- 明确入口的脚本或命令
- 有清晰输入输出契约的格式转换工具
- 能在沙箱中独立重放的程序类能力

### 2.2 本期明确不做

- 纯提示词沉淀
- 长链 workflow 自动拆解的全自动版本
- 团队级远程共享池
- 跨宿主完全一致的原生交互体验
- 无法构造验证用例的能力

### 2.3 MVP 的最小定义

MVP 只接受下面这种候选能力：

1. 单入口
2. 单一职责
3. 可单独执行
4. 输入输出可保存
5. 能用样例重放

满足这些条件的候选能力，才进入自动评估和候选池。其余能力先只记录，不做自动转正。

---

## 3. 设计原则

1. **程序类优先**：只做有执行反馈的能力，避免在第一版过度依赖主观语义判断。
2. **复现先于评估**：先证明它能被稳定重放，再讨论值不值得入库。
3. **验证强于描述**：能力说明可以错，测试和样本更重要。
4. **启发式不冒充证明**：AST、静态扫描、embedding 都只是线索，不是最终裁决。
5. **检索宁可漏召回，不要乱召回**：错误召回会污染宿主上下文，也会误导后续复用。
6. **血缘必须可追溯**：每次合并、拆分、晋升、降级都要有 lineage。
7. **先单人闭环，再团队扩展**：个人场景跑不稳，团队池只会放大噪声。

---

## 4. 系统分层

系统拆成 4 层，每层职责明确。

### 4.1 采集层

负责从不同 agent 收集运行轨迹，并统一转换为标准事件。

- Claude Code：优先使用 hooks 与 transcript
- Codex：优先使用结构化 session / JSONL / OTel
- Hermes：通过源码 hook 或 learning loop 集成

### 4.2 归档层

负责保存原始轨迹、代码快照、输入输出样本、文件变更、环境信息。

这一层不是知识库，而是证据库。

### 4.3 蒸馏层

负责做候选提取、重放、验证、粒度归一、相似聚类、合并与降级。

### 4.4 服务层

负责把已经转正的能力暴露出去。

- MCP：统一执行接口
- 宿主适配器：控制检索、排序、注入时机、权限与原生体验

这里要明确：**MCP 统一的是执行接口，不统一宿主的发现和注入体验。**

---

## 5. 正确性模型

这是 v0.2 最重要的修正。

### 5.1 不能再使用“跑通 = 正确”

一个工具成功执行，只能说明：

- 依赖没有炸
- 入口可以跑
- 当前样例没有触发明显异常

它不能直接说明：

- 输出是对的
- 输出质量达标
- 合并后语义没有漂移
- 这个工具值得长期复用

因此验证必须分层。

### 5.2 四层验证门禁

#### Gate 1：Replay Gate

目标：证明候选能力可以在隔离环境中被稳定重放。

检查内容：

- 依赖可安装
- 入口可执行
- 样例输入可复现
- 没有未声明的环境依赖

通过含义：它是“可运行”的。

#### Gate 2：Output Gate

目标：证明输出满足最低正确性要求。

可选手段：

- fixture 对比
- hash 对比
- 结构化字段断言
- 属性测试
- 快速人工抽样验收

通过含义：它不只是能跑，而且输出大致对。

#### Gate 3：Contract Gate

目标：证明输入输出契约清楚且可泛化。

检查内容：

- 输入类型可描述
- 输出类型可描述
- 错误条件可记录
- 无明显项目私有硬编码

通过含义：它有机会跨任务复用。

#### Gate 4：Promotion Gate

目标：决定它是继续做候选，还是晋升为正式能力。

考虑内容：

- 复用频次
- 跨项目复现
- 最近成功率
- 检索可召回性
- 是否与现有能力重复

### 5.3 Gate 的工程含义

- `Replay Gate` 通过，不等于可入库
- `Output Gate` 不通过，能力只能保留原始记录
- `Contract Gate` 不通过，能力只能作为项目私产，不进核心库
- `Promotion Gate` 通过，才进入正式能力库

## 6. 入库策略

### 6.1 两条晋升路径

为避免只靠 `N >= 3` 导致冷启动太慢，采用双路径。

#### 路径 A：统计晋升

适合普通候选能力。

条件建议：

- 至少 3 次实际复用
- 至少 1 次通过 `Output Gate`
- 最近成功率不低于阈值
- 没有被判定为近重复垃圾项

#### 路径 B：高质量单样本晋升

适合低频但明显值钱的能力。

条件建议：

- 明确输入输出契约
- 至少 1 套高质量 fixture
- 通过全部 4 个 Gate
- 被人工 `pin` 或被系统标记为高价值

### 6.2 状态机

每个能力单元的状态建议固定为：

- `raw`
- `candidate`
- `verified`
- `promoted`
- `deprecated`
- `archived`

推荐含义：

- `raw`：只记录轨迹与证据
- `candidate`：候选能力，等待重放与验证
- `verified`：可运行且通过输出验证
- `promoted`：正式入库，可被检索与调用
- `deprecated`：可用但不建议继续召回
- `archived`：归档，只保留血缘和历史

---

## 7. 粒度策略

### 7.1 MVP 不做“任意长链自动拆 DAG”

这件事方向没问题，但实现成本高，误判代价也高。

MVP 先使用更克制的策略：

- 只接受单入口能力
- 只接受单职责能力
- 不自动从任意长链里拆子图
- 对长链只做“候选片段标记”，留给后续版本做拆解

### 7.2 第一版最小单元判定

一个能力被视为可沉淀最小单元，需要同时满足：

1. 单一入口
2. 主动作单一
3. 可脱离原任务单独重放
4. 输入输出有固定边界
5. 可以构造独立验证样本

### 7.3 后续再升级到图级拆分

图级拆分放到阶段二或三再做，届时再引入：

- 调用链追踪
- 中间产物血缘
- 节点共享度统计
- 子图合成与回退

---

## 8. 合并策略

### 8.1 合并不是“谁像谁就并”

合并至少分 3 步：

1. 粗召回：embedding、关键词、签名特征、代码指纹找近邻
2. 结构比对：输入输出契约、入口模式、依赖、测试样本类型
3. 合并验证：对合并产物跑联合样本集

### 8.2 合并安全标准

只有同时满足下面条件，才允许自动合并：

1. 两者的核心任务描述一致或存在明确父子关系
2. 输入输出契约可统一
3. 联合样本集通过 `Replay Gate` 和 `Output Gate`
4. 合并后召回语义更清晰，而不是更模糊

### 8.3 合并结果优先形态

优先产生一个“父能力 + 特化适配”的结构，而不是强行把所有实现揉成一个文件。

推荐形态：

- 父能力：定义统一描述、统一检索入口、统一签名
- 子实现：保留按输入类型或依赖差异分叉的具体实现

示例：

- 父能力：`to-markdown`
- 子实现：`doc-to-md`
- 子实现：`pdf-to-md`
- 子实现：`ocr-pdf-to-md`

### 8.4 可回退设计

每次合并都必须保存：

- 合并前 manifest 快照
- 合并前实现引用
- 血缘关系
- 合并理由
- 失败样本与保留样本

一旦新样本暴露语义分叉，可以自动拆回父子结构或拆回独立能力。

## 9. 统一 Trace Schema v0.2

v0.1 的事件结构太薄，支撑不了复现和血缘分析。这里补成更可用的版本。

```json
{
  "event_id": "uuid",
  "session_id": "string",
  "project_id": "string",
  "task_id": "string",
  "host_agent": "claude-code | codex | hermes",
  "timestamp": "ISO8601",
  "event_type": "tool_call | generated_code | command_exec | file_edit | prompt",
  "name": "string",
  "cwd": "string",
  "source_ref": {
    "conversation_turn": "string",
    "message_id": "string",
    "code_block_id": "string"
  },
  "input_artifacts": [
    {
      "path": "string",
      "hash": "string",
      "media_type": "string"
    }
  ],
  "output_artifacts": [
    {
      "path": "string",
      "hash": "string",
      "media_type": "string"
    }
  ],
  "command": {
    "argv": ["string"],
    "exit_code": 0,
    "duration_ms": 1234
  },
  "stdout_ref": "string",
  "stderr_ref": "string",
  "env_fingerprint": {
    "os": "string",
    "runtime": "string",
    "dependencies_lock_hash": "string"
  },
  "file_changes": [
    {
      "path": "string",
      "change_type": "added | modified | deleted",
      "before_hash": "string",
      "after_hash": "string"
    }
  ],
  "result": {
    "status": "success | error",
    "error_type": "string",
    "error_message": "string"
  },
  "context_fingerprint": "string"
}
```

### 9.1 这些新增字段解决什么问题

- `task_id`：把多条事件绑定到同一任务
- `cwd`：提高重放成功率
- `input_artifacts` / `output_artifacts`：支撑验证、检索、血缘
- `command`：还原实际执行入口
- `stdout_ref` / `stderr_ref`：帮助诊断失败
- `env_fingerprint`：解释“为什么昨天能跑今天不能跑”
- `file_changes`：识别真实副作用

## 10. 静态分析的正确定位

### 10.1 能做什么

静态分析适合做：

- 硬编码路径扫描
- 密钥和敏感信息扫描
- 明显副作用 API 粗筛
- 依赖声明缺失检查
- 代码指纹和近重复初筛

### 10.2 不能宣称什么

静态分析不能可靠证明：

- 完全确定性
- 完全无副作用
- 真正的最小可复用粒度
- 输出语义是否正确

### 10.3 文档层面的正确表述

后续所有方案文档建议统一使用这种措辞：

- `AST / 静态扫描用于启发式筛查`
- `副作用与稳定性主要通过沙箱重放和样本验证确认`

## 11. 检索与注入

### 11.1 检索目标

检索阶段不是把“最像的能力”找出来，而是把“最值得尝试且误召回风险最低的能力”排在前面。

### 11.2 排序建议

排序分数可由这几项构成：

- 语义相似度
- 输入输出契约匹配度
- 最近成功率
- 失败惩罚
- 作用域匹配度
- 新鲜度

### 11.3 注入策略

宿主上下文里默认只注入 L1 元数据：

- 名称
- 一句话描述
- 适用条件
- 输入输出签名
- 最近质量分

模型明确请求展开后，再加载：

- 实现说明
- 参数细节
- 测试样本
- 血缘记录

### 11.4 MCP 的准确定位

MCP 负责：

- 统一调用入口
- 暴露能力接口
- 管理工具描述

宿主适配器负责：

- 何时检索
- 检索多少条
- 如何排序
- 是否自动注入
- 是否需要权限确认

## 12. 数据存储建议

### 12.1 目录结构

```text
distiller/
  traces/
  artifacts/
  candidates/
  skills/
  indexes/
  lineage/
  fixtures/
```

### 12.2 各目录职责

- `traces/`：原始事件和会话级轨迹
- `artifacts/`：输入输出样本、日志、代码快照
- `candidates/`：尚未转正的候选能力
- `skills/`：已转正能力
- `indexes/`：向量索引、倒排索引、代码指纹索引
- `lineage/`：合并、拆分、晋升、降级记录
- `fixtures/`：公共验证样本集

## 13. MVP 方案

### 13.1 宿主

先只做 Claude Code。

原因：

- 采集入口清晰
- 闭环最短
- 方便控制测试环境

### 13.2 工具范围

先只做“文档转换到 Markdown”这一大类，但内部仍要求单入口单职责。

可接受示例：

- `pdf-to-md`
- `docx-to-md`
- `html-to-md`

暂不接受示例：

- `meeting-recording-to-blog-post`
- `video-to-script-to-video`
- `research-pipeline`

### 13.3 自动化范围

MVP 里自动化到这里为止：

1. 轨迹采集
2. 候选发现
3. 沙箱重放
4. 基础输出验证
5. 近重复粗筛
6. 正式能力检索与 MCP 暴露

MVP 里先不自动化：

- 任意长链拆分
- 全自动安全合并
- 团队共享
- 提示词沉淀

### 13.4 成功标准

MVP 成功不靠“看起来很智能”，而靠 5 个指标：

1. 至少沉淀出 20 个可验证能力
2. Top 3 检索命中率达到目标阈值
3. 重复生成相似工具的比例明显下降
4. 至少 1 类任务出现 warm-start 收益
5. 人工审核不在关键路径上

## 14. 指标体系

### 14.1 核心指标

- `Replay Pass Rate`
- `Output Pass Rate`
- `Promotion Rate`
- `Top-1 Recall`
- `Top-3 Recall`
- `Merge Precision`
- `Warm-start Gain`
- `Review Load`

### 14.2 指标解释

- `Replay Pass Rate`：候选能力中可稳定重放的比例
- `Output Pass Rate`：重放后输出达标的比例
- `Promotion Rate`：候选能力中最终转正的比例
- `Top-1 Recall` / `Top-3 Recall`：检索命中质量
- `Merge Precision`：自动合并里真正合理的比例
- `Warm-start Gain`：带库相对空库的效率收益
- `Review Load`：每转正一个能力需要多少人工分钟

## 15. 路线图

### 阶段一

- Claude Code 采集
- 文档转 Markdown 类工具
- 双 Gate 验证：Replay + Output
- MCP 服务层
- 单人本地库

### 阶段二

- 接 Codex
- 完善 Contract Gate 和 Promotion Gate
- 增加父能力 + 子实现合并模型
- 引入更完整的检索排序

### 阶段三

- 接 Hermes
- 做长链拆分实验
- 做团队共享池
- 引入签名、权限、沙箱治理

## 16. 待拍板事项

1. 是否接受 `MVP = Claude Code + 文档转 Markdown + 单人本地库`
2. 是否接受 `N >= 3` 只是统计晋升路径，不是唯一晋升路径
3. 是否接受 `Replay Gate` 和 `Output Gate` 分离，不再把“跑通”视作“正确”
4. 是否接受第一版不做任意长链自动拆解
5. 是否接受 MCP 只作为统一执行层，而不是统一宿主体验层

## 17. 一句话结论

这个项目依然可行，而且方向不错；真正决定它能不能落地的，不是“概念是否完整”，而是你愿不愿意把 MVP 收得足够窄，并把验证、复现、血缘和回退这些底层约束先做扎实。
