# 员工蒸馏器 · 外部参考导读与实施顺序

> 目标：给 CC 一个**不用整库通读**的外部参考导读。
> 这份文档只回答三件事：
> 1. 先看哪个项目
> 2. 在那个项目里只看哪些 part
> 3. 这一 part 到底借来干什么
>

1. **主参考**
   - `Yunjue-Agent`
   - `Letta Code / MemFS`

2. **辅助参考**
   - `Mem0`
   - `Graphiti / Zep`

3. **后置参考**
   - `MCP Registry`
   - `Smithery`
   - `Composio`

4. **产品启发，不作实现参考**
   - `Devin`
   - `OpenHands`

最重要的一句：

**CC 不需要读完整个 Yunjue，也不需要读完整个 Letta。只看下面列出来的 part 就够了。**

## 3. 主参考 1：Yunjue-Agent

### 3.1 只看这些 part

#### Part A：项目总览和术语

看：

- [Yunjue-Agent README](https://github.com/YunjueTech/Yunjue-Agent/blob/main/README.md)

重点看什么：

- `Tool-First Evolutionary Principle`
- `Parallel Batch Evolution`
- `zero-start`
- `warm-start`

借来干什么：

- 定义我们系统里的“工具演化主循环”
- 明确为什么先做 `reuse-before-create`

不用看什么：

- benchmark 成绩细节
- web demo 展示层

#### Part B：任务先复用还是新建

看：

- [src/prompts/templates/step_tool_analyzer.md](https://raw.githubusercontent.com/YunjueTech/Yunjue-Agent/main/src/prompts/templates/step_tool_analyzer.md)

重点看什么：

- `Exhaustive available Tool Check`
- `Only request new tools if this task can not be achieved using available tools`
- `NEVER create a composite tool`

借来干什么：

- 我们的 `retrieve -> decide -> create` 主循环
- warm-start 前的“先找现有能力，不够再造”

不要直接照抄什么：

- 它把“atomic tool”理解得更细，更接近研究型 tool decomposition
- 我们这里最小单元是“自洽目的”，不是最小函数

#### Part C：聚类与功能判同

看：

- [src/prompts/templates/tool_cluster.md](https://raw.githubusercontent.com/YunjueTech/Yunjue-Agent/main/src/prompts/templates/tool_cluster.md)

重点看什么：

- 它怎么让 LLM 判“两个工具是不是同一个 fundamental action”
- 它为什么反对“detect-then-dispatch”

借来干什么：

- 学它的“先召回再裁决”的聚类工作流
- 学它让 LLM 做语义裁决的方式

明确不要照抄什么：

- 它是按**名字 + 描述**聚类
- 它反对 `mode/type/format` 分派

我们这里必须改成：

- 主轴看 `contract_signature + purpose`
- `dispatch` 在我们这里恰恰是合法终态

#### Part D：批量演化与复现入口

看：

- [reproduce/docs/reproduce.md](https://raw.githubusercontent.com/YunjueTech/Yunjue-Agent/reproduce/docs/reproduce.md)

重点看什么：

- `WORKER_TOOL_ENHANCE_INTERVAL`
- `batch_size`
- `scripts/evolve.sh`
- `scripts/evaluate.py`

借来干什么：

- 学它“不是每来一个碎片就即时合并，而是先入批次缓冲再统一处理”
- 学它如何把演化和评估拆成固定批处理入口

不要直接照抄什么：

- 不要照抄它的评测数据集
- 不要照抄它的 Merger 思维

### 3.2 Yunjue 这边到底借哪几个模块

直接借：

- `retrieve -> decide -> create`
- `R_miss` 思路
- batch evolution 调度
- 执行级二元反馈

自己重写：

- `contract extraction`
- `same_purpose / same_branch / iteration` 判定
- `Merger -> Composer`

一句话：

**Yunjue 只借骨架，不借中间发动机。**

## 4. 主参考 2：Letta Code / MemFS

### 4.1 只看这些 part

#### Part A：MemFS

看：

- [MemFS docs](https://docs.letta.com/letta-code/memfs/)

重点看什么：

- git-backed memory filesystem
- memory 以目录和 markdown 文件形式存在
- 版本历史、冲突处理、直接检查和编辑

借来干什么：

- 我们的 `skills/` 仓库形态
- `lineage / iteration_log / branches` 的落盘方式

#### Part B：Letta Code Memory

看：

- [Letta Code Memory docs](https://docs.letta.com/letta-code/memory/)

重点看什么：

- memory 的组织方式
- agent 如何读写 memory
- MemFS 在本地和 API 模式下的行为

借来干什么：

- 渐进式披露
- 外部服务如何把能力库作为“可检索上下文仓库”来暴露

#### Part C：Shared Memory

看：

- [Shared memory docs](https://docs.letta.com/guides/core-concepts/memory/shared-memory/)

重点看什么：

- 多 agent 共享 memory block 的语义

借来干什么：

- 后续团队共享池的概念模型
- 暂时不用实现，但能提前校准数据隔离和共享边界

#### Part D：Remote Environments

看：

- [Remote environments](https://docs.letta.com/letta-code/remote/)

重点看什么：

- agent 跨执行环境时，memory 跟着走

借来干什么：

- 想清楚未来“宿主变了，但能力库还是同一个”的边界

### 4.2 Letta 这边到底借哪几个模块

直接借：

- `git-backed memory repository`
- `progressive disclosure`
- `memory as filesystem`

自己重写：

- 契约引擎
- 分支/迭代分类器
- Composer

一句话：

**Letta 借仓库层，不借增长逻辑。**

## 5. 辅助参考 1：Mem0

### 5.1 只看这些 part

看：

- [Memory Types](https://docs.mem0.ai/core-concepts/memory-types)
- [Memory Evaluation](https://docs.mem0.ai/core-concepts/memory-evaluation)
- [Entity-Scoped Memory](https://docs.mem0.ai/platform/features/entity-scoped-memory)

重点看什么：

- factual / episodic / semantic memory 的分层
- extraction vs retrieval 两阶段
- entity scope：user / agent / app / session

借来干什么：

- 我们自己的 scope 设计：
  - 个人能力
  - 项目能力
  - 团队能力
- `memory write` 和 `memory read` 的分层语义

不用深读什么：

- 托管平台细节
- 平台接入 SDK

一句话：

**Mem0 用来想“记忆怎么分层”，不是用来想“工具怎么长”。**

## 6. 辅助参考 2：Graphiti / Zep

### 6.1 只看这些 part

看：

- [Graphiti Overview](https://help.getzep.com/graphiti/getting-started/overview)
- [Understanding the Graph](https://help.getzep.com/v2/understanding-the-graph)

重点看什么：

- temporal knowledge graph
- evolving relationships over time
- graph + semantic + full-text 混合检索

借来干什么：

- 后续如果要表达“能力之间、分支之间、项目之间”的时序关系，可以借它的 graph 思维

现在不要过度使用什么：

- 不要让图谱先于契约引擎
- 不要一上来把能力库做成图数据库项目

一句话：

**Graphiti 用来增强关系表达，不是 MVP 发动机。**

- [Devin intro](https://docs.devin.ai/get-started/devin-intro)

- 它更像 orchestration shell / control center

**这两个给产品感，不给发动机。**

## 9. 给 CC 的实施顺序

这是最重要的一段。

### 第 1 步：搭主循环

参考：

- Yunjue `README`
- `step_tool_analyzer.md`

要做的模块：

- `retrieve -> decide -> create/reuse`
- `R_miss` 缩作用域版本

### 第 2 步：搭仓库层

参考：

- Letta `MemFS`
- Letta `Memory`

要做的模块：

- `skills/` 仓库
- `branches/`
- `iteration_log`
- `lineage`

### 第 3 步：自己实现契约引擎

参考：

- 我们自己的 [员工蒸馏器-契约引擎设计.md](</D:/interact/员工蒸馏器-契约引擎设计.md>)
- 修改意见：[员工蒸馏器-契约引擎设计-修改意见.md](</D:/interact/forcodex/员工蒸馏器-契约引擎设计-修改意见.md>)

要做的模块：

- `contract_signature`
- `branch_identity`
- `behavior_signature`
- `same_purpose / same_branch / iteration` 判定

### 第 4 步：搭批量吸收 + Composer

参考：

- Yunjue `reproduce/docs/reproduce.md`

要做的模块：

- batch buffer
- periodic absorb
- `Composer`

不要做的模块：

- canonicalizing merger

### 第 5 步：再考虑辅助增强

参考：

- Mem0
- Graphiti
- MCP Registry / Smithery / Composio

要做的模块：

- scope model
- richer relationship graph
- registry / auth / hosted MCP
