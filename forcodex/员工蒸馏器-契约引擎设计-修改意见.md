# 员工蒸馏器 · 契约引擎设计修改意见

> 目标：把 `员工蒸馏器-契约引擎设计.md` 里几个还偏粗、容易误判或误洗掉价值的地方补实，方便直接交给 CC 修改。
> 参考对象：`员工蒸馏器-契约引擎设计.md`
> 日期：2026-06-20

---

## 1. 修改目标

这轮不是改方向，而是补几个关键边界，让契约引擎从“方向对”变成“更难误伤好工具”。

重点收 5 个问题：

1. 分支判定不能过度依赖 `input media_type`
2. 契约签名缺少行为/输出手艺指纹
3. `R_miss` 作用域过大，容易误伤 warm-start
4. `best-of-N` 和“保年轮”之间有冲突，需要收束
5. `shared_post_processing` 的提级门槛还不够硬

---

## 2. 问题 1：分支判定过度依赖 `input media_type`

### 当前位置

- §3 契约签名
- §5 三选一分类

对应文中大意：

- 输入契约以 `input_artifacts.media_type / 扩展名 / arity` 为主锚
- `C.输入媒体类型 ∉ S.branches` 就判成 `same_purpose_new_branch`

### 问题

这个粒度太粗，容易把真实世界里重要的路径差异压扁。

典型风险：

- `pdf` 内部可能有“文本版 / 扫描版”两条完全不同路径
- `单文件 / 目录模式` 其实可能是不同入口形态
- 是否产生 `assets`、是否保留图片、是否需要修复中间格式，都可能影响分支身份
- `.doc` 和 `.docx` 又可能在升级转换后收敛到同一分支

也就是说，**媒体类型只能做粗信号，不能直接当 branch identity。**

### 风险

- 误把“同分支迭代”判成“新分支”
- 误把“新分支”判成“同分支重复/迭代”
- 后续会导致分支爆炸，或者把重要能力压进错误分支

### 建议改法

把 “分支身份” 从 `media_type` 升级成一个更完整的 `branch_identity`，至少包含：

- `input_mode`
  例：`single_file | directory`
- `normalized_input_family`
  例：`pdf_text | pdf_scanned | office_docx | office_legacy`
- `artifact_profile`
  例：是否产出 `assets`、是否含图片旁产物
- `determinism`
  例：`deterministic | nondeterministic | mixed`
- `key_flags`
  例：是否需 repair、是否为 wrapper fallback

### 建议落点

1. 在 §3 “契约签名”里补一个 `branch_identity` 段
2. 在 §5 三选一分类里把判定条件从

```text
C.输入媒体类型 ∉ S.branches
```

改成

```text
C.branch_identity 与现有 branches 都不兼容
```

3. 加一句：`media_type` 只是 `branch_identity` 的组成部分，不是分支主键

## 3. 问题 2：契约签名缺少 `behavior_signature`

### 当前位置

- §3 契约签名
- §4 目的判同

### 问题

现在契约三件套是：

- 输入契约
- 输出契约
- 目的摘要

这足够找近邻，但还不足以区分“外部 I/O 看起来一样、内部输出手艺差很多”的能力。

以 `doc2md` 为例，真正值钱的不是：

- 输入是文档
- 输出是 markdown + assets

而是：

- 表格是否转成列表
- 阅读顺序是否重建
- 键值表是否特判
- 图片是否正确落盘和引用

这些东西如果不进签名，薄壳 wrapper 和成熟实现会在契约层看起来过于相似。

### 风险

- 把“有年轮的成熟分支”和“薄壳兜底分支”误判成同类
- 在同目的下错并不同输出风格的能力
- 把真正的价值差异丢到人工兜底里，自动判定太盲

### 建议改法

在契约签名里新增一个 `behavior_signature`，来源于 Output Gate 的属性验证结果。

建议包含：

- `markdown_valid`
- `assets_emitted`
- `image_ref_coverage`
- `heading_preservation`
- `table_render_mode`
  例：`pipe_table | kv_list | row_list`
- `key_value_rendering`
- `content_coverage_grade`
- `is_thin_wrapper`

### 建议落点

1. 在 §3 “契约签名：从 trace 碎片抽什么”中，把“三件套”改成“四件套”
2. 在 §4 “目的判同”里补一句：LLM 裁决输入除了契约签名和目的摘要，还应看到 `behavior_signature`
3. 在 §5 中说明：同一 `purpose` 下，`behavior_signature` 明显不同的实现，不应直接判重复

## 4. 问题 3：`R_miss` 作用域过大

### 当前位置

- §1 从 Yunjue 借什么
- §11 warm-start 相关语义可同步补

### 问题

现在写法容易让人理解成：某个目的下试过失败的工具，就不要再推荐。

这在真实系统里太粗了。一次失败可能只是：

- 某个坏样本
- 某个坏环境
- 某个旧版本
- 某个旧分支

不应该把整个目的级能力一起拉黑。

### 风险

- warm-start 变得过度保守
- 一次偶发失败导致后续长期不复用
- 分支已经修好后，旧失败缓存还在继续误导系统

### 建议改法

把 `R_miss` 的作用域收紧成：

```text
skill / branch + contract_slice + version + env_fingerprint
```

并明确失效规则：

- 分支迭代后失效
- 环境变化后失效
- 命中不同 contract slice 时不沿用

### 建议落点

1. 在 §1 第 1 点补一句：`R_miss` 不是目的级黑名单，而是分支/版本/环境级失败记忆
2. 在 warm-start 章节补一句：推荐时要先检查 `R_miss` 是否仍对当前 `branch_identity + env_fingerprint` 生效

## 5. 问题 4：`best-of-N` 和“保年轮”之间有张力

### 当前位置

- §1 从 Yunjue 借什么
- §2 Composer 替换 Merger
- §6 Batch Evolution

### 问题

文中借了 Yunjue 的 batch evolution，并提到可以 `best-of-N` 为每个分支择优实现。

但如果“择优”的含义不讲清楚，很容易又滑回 canonicalization：

- 旧实现被新实现覆盖
- 旧年轮被视作次优垃圾
- fixture 没覆盖到的边缘处理被悄悄洗掉

这和“原样保留变体、保留伤疤”的总原则有内在冲突。

### 风险

- 表面上没在做 Merger，实际上通过“择优替换”把旧价值抹掉
- lineage 变成有记录但没用，因为默认路径已经悄悄丢价值

### 建议改法

把 `best-of-N` 明确成：

- 只能决定“默认激活实现”
- 不能删除旧实现
- 不能覆盖 lineage
- 不能跳过回归

也就是说，应区分：

- `active_branch_impl`
- `retained_impls`

### 建议落点

1. 在 §1 第 3 点“Batch Evolution”补充说明：best-of-N 只选默认实现，不删除兄弟实现
2. 在 §2 的 Composer 表格里补一行：`默认激活实现可切换，但所有历史实现保留可回退`
3. 在 §6 端到端流程里补一句：Composer 写回时保留旧实现引用，不做覆盖式替换

## 6. 问题 5：`shared_post_processing` 提级门槛不够硬

### 当前位置

- §2 Composer
- §6 Batch Evolution

### 问题

“把跨分支通用后处理提到父级”这个方向是对的，但现在规则太松，容易把局部分支的修补误提升成全局共享逻辑。

像 `table_to_list` 这种东西，看起来很共享，但未必对所有 branch 都是纯增益。

### 风险

- 一个分支的好修补被错误推广到全部分支
- shared 层变成新的隐性污染源
- 回归复杂度上升，而且问题更难定位

### 建议改法

把 “提级到 shared” 设成独立门槛，至少要求：

1. 被 2 个及以上分支显式受益
2. 提级前后共享回归全部通过
3. 没有任何兄弟分支出现质量回退
4. 提级后仍保留“降回 branch 层”的回退能力

### 建议落点

1. 在 §2 Composer 一节补一个小段：`shared promotion policy`
2. 在 §6 端到端流程里，Composer 后增加一行：

```text
shared_candidate evaluation → cross-branch regression → promote or keep local
```

3. 在文末一句话结论附近补一句：共享后处理不是默认提级，而是有门槛的二次晋升

---

## 7. 建议新增的三个术语

为了让文档后面更稳，建议显式引入这 3 个术语：

- `branch_identity`
  用来替代“输入媒体类型 = 分支”

- `behavior_signature`
  用来承接 Output Gate 里那些真正体现输出手艺的属性

- `shared_promotion`
  用来描述从 branch 层修补上升到 shared_post_processing 的独立过程

---

## 8. 建议修改顺序

给 CC 的建议顺序：

1. 先改 §3 契约签名，补 `branch_identity` 和 `behavior_signature`
2. 再改 §4/§5，把三选一分类条件从 `media_type` 提升到 `branch_identity`
3. 再改 §1/§6，收紧 `R_miss` 和 `best-of-N`
4. 最后改 §2/§6，补 `shared_post_processing` 的提级门槛

---

## 9. 一句话要求

这轮修改的原则不是“加更多复杂度”，而是避免系统在最关键的地方把好东西看成噪声、把年轮看成冗余、把一次失败看成永久否定。
