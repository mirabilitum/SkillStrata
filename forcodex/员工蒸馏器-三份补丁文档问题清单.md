## 1. 总体判断

这三份文档方向基本对，已经从“相似度合并”转向了 v0.4 要的主脊：

```text
采集 -> 重放 -> 属性 Output Gate -> behavior_signature
     -> 契约抽取 -> 三选一分类 -> Composer -> MCP 回灌
```

但还有几个需要补硬的地方：

- `Output Gate` 的硬阈值还不够 branch-aware，容易误杀扫描版、低文本、表格型文档。
- `behavior_signature` 已经提出了，但还缺正式 schema 和字段级偏序定义。
- `hook <5ms` 和“证据链完整”之间有张力，需要拆成 raw event 与 enrichment 两阶段。
- MCP 被动 warm-start 如果暴露太多 promoted tool，会污染宿主工具列表。
- 三选一阈值把 `behavior_signature` 当偏序是对的，但字段里有不少分类项不能天然比较。
- `shared_promotion` 还缺 pipeline 顺序、幂等、双重应用和容差规则。

## 2. 属性 Output Gate 与 behavior_signature

### P1：文本覆盖率硬阈值会误杀合法分支

位置：

- `员工蒸馏器-属性OutputGate与behavior_signature.md:89`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:93`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:94`

问题：

文档把“文本覆盖比 >= 0.9”设成硬门禁，但 `doc2md` 类能力并不总是文本主导。扫描版 PDF 的合法输出可能是“每页图片引用 + assets”，低文本 PPT/XLSX 也可能主要靠表格、图片、sheet/page 结构保真。

风险：

- 扫描版 PDF 被误判 fail。
- 表格型 Excel、图片型 PPT 被误判“大段丢字”。
- 系统偏向文本抽取工具，压制“保旁产物”的成熟分支。

建议：

把硬阈值改成 `branch_identity` 或 `input_profile` 感知的门禁。

示例：

```text
pdf_text       -> 文本覆盖为硬项
pdf_scanned    -> 页面图片覆盖 / assets 引用覆盖为硬项
xlsx_table     -> 表格单元格数据覆盖为硬项
pptx_mixed     -> slide/page 数 + 文本/图片覆盖组合为硬项
```

需要补到文档：

- 在 §5 “门禁阈值”里增加 `input_profile` 分支表。
- 不要用一个全局 `text_coverage >= 0.9` 管所有输入。

### P1：独立抽取器要求还不够严格

位置：

- `员工蒸馏器-属性OutputGate与behavior_signature.md:49`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:51`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:52`

问题：

文档要求“输入侧测量必须用独立工具”，这是对的。但例子里提到 `markitdown / pdfminer`，还需要明确“独立”的判据：不能和候选分支共享同一个核心抽取库，否则仍然可能形成循环。

例如：

- `process_generic` 本身就是 `markitdown` 薄壳，则不能再用 `markitdown` 当它的输入侧独立 oracle。
- 如果某个 PDF 分支内部也用 `pdfminer`，输入测量侧再用 `pdfminer` 就不独立。

风险：

- 候选实现漏掉某类内容，输入测量也跟着漏，系统误判守恒。
- 薄壳 fallback 被错误认为有可靠 Output Gate。

建议：

补一个 `oracle_independence` 规则：

```text
input_measurement_extractor 与 candidate.impl 不能共享同一核心解析库；
若无法满足独立性，则 Output Gate 降级为 soft evidence，不允许作为自动晋升硬证据。
```

### P1：`behavior_signature` 缺正式 schema 与字段级偏序

位置：

- `员工蒸馏器-属性OutputGate与behavior_signature.md:61`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:65`
- `员工蒸馏器-三选一阈值与shared_promotion.md:20`
- `员工蒸馏器-三选一阈值与shared_promotion.md:37`

问题：

`behavior_signature` 已经列了字段，但还没有定义：

- 字段类型
- 字段取值范围
- 哪些字段可比较
- 哪些字段只能判相等/不同
- 哪些字段有明确“更好/更差”的偏序

比如 `content_coverage_grade` 可以有 A > B > C，但 `table_render_mode = pipe_table | kv_list | row_list` 并不天然存在全局优劣。对某些输入，`pipe_table` 可能更忠实；对 LLM 读取，`kv_list` 可能更友好。

风险：

- 后续“C 支配 B”会把风格差异误判成能力升级。
- 同目的下本该并列保留的输出手艺，被错误压成单一 active 实现。

建议：

新增 `behavior_signature schema`，并给每个字段定义比较规则：

```yaml
content_coverage_grade:
  type: ordinal
  order: [D, C, B, A]

image_ref_coverage:
  type: numeric
  better: higher
  tolerance: 0.02

table_render_mode:
  type: categorical
  compare: equal_or_different
  no_global_order: true

key_value_rendering:
  type: boolean
  compare_scope: only_when_input_profile_is_key_value_table
```

### P2：表格数据守恒需要规范化，否则会大量误报

位置：

- `员工蒸馏器-属性OutputGate与behavior_signature.md:42`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:46`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:54`

问题：

“检查每个单元格数据是否出现在输出某处”的方向对，但真实文档会有大量格式噪声：

- 空格、全角半角
- 日期格式变化
- 数字精度变化
- 合并单元格
- 重复单元格
- 换行拆分

风险：

- 明明内容保住了，却因为格式变化被判丢表。
- 重复值、空值、合并格导致覆盖率虚高或虚低。

建议：

补 `cell_normalization` 与 `matching_policy`：

```text
Unicode NFKC
去多余空白
数字/日期规范化
短文本 exact match
长文本 token containment
重复值按 multiset 计数
合并单元格单独标记
```

### P2：`is_thin_wrapper` 应该记录基线版本和差异层级

位置：

- `员工蒸馏器-属性OutputGate与behavior_signature.md:79`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:82`
- `员工蒸馏器-属性OutputGate与behavior_signature.md:85`

问题：

“和 markitdown 几乎一样 = 薄壳”方向对，但 `markitdown` 版本、配置、依赖变化会影响输出。只存布尔值 `is_thin_wrapper` 不够。

风险：

- markitdown 升级后薄壳判断漂移。
- “薄壳 + 小但重要的后处理”被误标为纯薄壳。

建议：

把 `is_thin_wrapper` 扩成：

```yaml
thin_wrapper:
  value: true
  baseline: markitdown
  baseline_version: x.y.z
  similarity_score: 0.97
  custom_delta:
    - none | light_postprocess | asset_handling | table_transform
```

## 3. 技术栈与运行时 canonical

### P1：`<5ms hook` 和完整证据链之间需要两阶段设计

位置：

- `员工蒸馏器-技术栈与运行时-canonical.md:38`
- `员工蒸馏器-技术栈与运行时-canonical.md:60`
- `员工蒸馏器-技术栈与运行时-canonical.md:61`
- `员工蒸馏器-技术栈与运行时-canonical.md:66`

问题：

文档要求 hook 极轻、静默、<5ms，这是对的。但同一段又说 hook 归一成含 `input/output_artifacts`、`determinism_signals` 占位的 `ToolCallEvent`。真实落地时，hook 不解析、不 hash、不扫描文件，就很难知道完整输入输出 artifact。

风险：

- 为了完整证据链，hook 变重，破坏无感。
- 为了无感，hook 只写粗事件，后续 daemon 缺少足够引用，证据链断。

建议：

明确拆成两种事件：

```text
RawToolEvent:
  hook 同步写入，只含宿主给到的原始信息、cwd、tool name、command/input refs、timestamp。

EnrichedToolEvent:
  daemon 空闲时补全，含 input_artifacts/output_artifacts/hash/media_type/file_changes/determinism_signals。
```

需要补一句：

```text
hook 永远只产 RawToolEvent；ToolCallEvent 是 daemon enrichment 后的产物。
```

### P1：daemon 延迟处理可能错过 artifact 快照

位置：

- `员工蒸馏器-技术栈与运行时-canonical.md:80`
- `员工蒸馏器-技术栈与运行时-canonical.md:101`
- `员工蒸馏器-技术栈与运行时-canonical.md:146`

问题：

文档设计为 daemon 空闲触发、延迟批量处理。这个符合“无感”，但如果 artifact 只在工作区临时存在，daemon 等到空闲再处理时，输入/输出/临时代码可能已经被覆盖、删除或继续编辑。

风险：

- Replay Gate 找不到原始输入。
- Output Gate 用到的输出已不是当时那份。
- lineage 里的实现快照缺失。

建议：

增加一个非常轻的 `snapshot request` 机制：

- hook 只记录候选路径和事件引用
- `Stop` hook 或 daemon early pass 做一次轻量 artifact snapshot
- snapshot 仍然不在前台重解析，但要尽快拷贝关键文件到 `artifacts/`

也可以规定：

```text
RawToolEvent -> SnapshotJob -> EnrichedToolEvent
```

### P1：MCP 暴露 promoted 能力会污染工具列表

位置：

- `员工蒸馏器-技术栈与运行时-canonical.md:121`
- `员工蒸馏器-技术栈与运行时-canonical.md:123`
- `员工蒸馏器-技术栈与运行时-canonical.md:124`
- `员工蒸馏器-技术栈与运行时-canonical.md:126`

问题：

文档说 MCP server 把 `skills/` 里 promoted 能力暴露成 MCP tool。MVP 只有 `doc_to_markdown` 时没问题，但系统一旦长起来，直接暴露所有 promoted 能力会污染宿主工具列表，也会增加模型误召回风险。

这和 v0.4 的“检索宁可漏召回，不要乱召回”有冲突。

建议：

把 MCP 暴露方式拆成两层：

```text
固定少量基础工具：
  distiller.search_capability
  distiller.describe_capability
  distiller.run_capability

高置信/高频能力：
  可选导出为一等 MCP tool，例如 doc_to_markdown
```

并补一个 promoted -> exposed 的二次门槛：

- 最近成功率
- 复用频次
- R_miss 低
- 契约足够稳定
- 工具描述短且不污染上下文

### P2：`Sandbox Workspace Touch = 0` 需要限定到 daemon/replay

位置：

- `员工蒸馏器-技术栈与运行时-canonical.md:101`
- `员工蒸馏器-技术栈与运行时-canonical.md:198`

问题：

文档把 `Sandbox Workspace Touch = 0` 写成无感指标。但 MCP server 真正被用户调用时，某些 promoted tool 必然要读取用户给的输入文件、可能写出 `.md` 和 `assets/` 到指定路径。

风险：

- 指标定义不清，导致合法的 MCP 工具执行也被记成违规。

建议：

改成：

```text
Daemon Replay Workspace Touch = 0
```

并区分：

- daemon/replay：永不碰工作区，只用 artifact 副本
- MCP user-invoked execution：可按用户授权读写目标路径

### P2：系统依赖分支不能只靠 `uv venv`

位置：

- `员工蒸馏器-技术栈与运行时-canonical.md:91`
- `员工蒸馏器-技术栈与运行时-canonical.md:101`
- `员工蒸馏器-技术栈与运行时-canonical.md:102`
- `员工蒸馏器-技术栈与运行时-canonical.md:170`

问题：

`uv per-tool venv` 很适合纯 Python，但 `doc2md.py` 真实终态包含 LibreOffice、Office COM、系统字体、平台差异这类系统依赖。文档说 Docker 阶段二再上，但 MVP 又以 `doc2md` 为终态尺子，两者之间有口径张力。

建议：

在 MVP 中明确：

- 纯 Python 分支：`uv venv`
- 系统依赖分支：记录为 `requires_host_capability`，不自动转正，或使用 host capability profile
- 阶段二再为 LibreOffice/COM 类分支接 Docker/host adapter

否则 Replay Gate 会把真实有价值但有系统依赖的分支误判为失败。

### P2：hook 静默失败需要带外错误计数

位置：

- `员工蒸馏器-技术栈与运行时-canonical.md:67`
- `员工蒸馏器-技术栈与运行时-canonical.md:68`

问题：

“失败也静默退出”对前台体验是对的，但如果没有带外计数，采集失败会长期不可见。

建议：

补一个轻量带外错误记录：

```text
hook 不向 stdout/stderr 输出；
但可向 distiller/internal_error.log 或 meta.sqlite counters 记录 failure_count。
```

并把 `Capture Drop Rate` 加到无感/可靠性指标里。

## 4. 三选一阈值与 shared_promotion

### P1：偏序规则不能直接套在所有 `behavior_signature` 字段上

位置：

- `员工蒸馏器-三选一阈值与shared_promotion.md:20`
- `员工蒸馏器-三选一阈值与shared_promotion.md:25`
- `员工蒸馏器-三选一阈值与shared_promotion.md:37`
- `员工蒸馏器-三选一阈值与shared_promotion.md:54`

问题：

“支配 / 相等 / 不可比”的思想是对的，但前提是每个字段都定义了可比较关系。当前 `behavior_signature` 里有不少字段不是天然有序的。

例子：

- `table_render_mode` 不一定 `kv_list > pipe_table`
- `key_value_rendering=true` 只在输入确实是键值表时才有意义
- `is_thin_wrapper=false` 也不一定总是更好，薄壳 fallback 可能更稳、更轻

建议：

先补字段级偏序 schema，再使用“支配”。

如果字段没有全局顺序，只能参与：

- 相等判定
- 差异判定
- ambiguous 判定

不能参与 `>=`。

### P1：`R_miss` 成功修复不能单独判定 iteration

位置：

- `员工蒸馏器-三选一阈值与shared_promotion.md:24`
- `员工蒸馏器-三选一阈值与shared_promotion.md:31`
- `员工蒸馏器-三选一阈值与shared_promotion.md:32`

问题：

“B 失败、C 成功”是很强的信号，但不能单独判定 C 是更好的迭代。B 可能是环境失败、依赖失败、超时；C 可能只是绕开了复杂路径，输出更少但没报错。

建议：

把第 1 条改成：

```text
C 在同 env_fingerprint 下跑过 B 的 R_miss 输入，
且 C 通过 Output Gate，
且 C 在 B 的既有 fixture 上无回退，
才判 iteration。
```

否则应该进入 ambiguous，而不是直接 iteration。

### P1：`B 支配 C -> 丢 C` 可能洗掉有用 fallback

位置：

- `员工蒸馏器-三选一阈值与shared_promotion.md:40`
- `员工蒸馏器-三选一阈值与shared_promotion.md:41`

问题：

如果 B 的输出指纹更强，C 未必就是没价值。C 可能：

- 依赖更少
- 更快
- 在某些环境可运行
- 适合作为 fallback
- 适合低资源模式

这正是 v0.4 “保年轮、保回退”的精神。

建议：

改成：

```text
behavior_signature(B) 支配 C
且 dependency_profile / runtime_profile / env_profile 无优势
才 duplicate 丢弃 C；
否则 C 进入 retained_impls，标为 fallback。
```

### P2：shared_promotion 需要处理 pipeline 顺序和幂等

位置：

- `员工蒸馏器-三选一阈值与shared_promotion.md:58`
- `员工蒸馏器-三选一阈值与shared_promotion.md:64`
- `员工蒸馏器-三选一阈值与shared_promotion.md:74`

问题：

把某个后处理 P 提到父级，不只是“能不能作用于 md 字符串”。还要回答：

- 它在 shared pipeline 的第几步？
- 它和已有 shared 后处理是否可交换？
- 它重复执行是否幂等？
- 从 branch 层移到 shared 后，会不会双重应用？

例子：

- `sanitize_text` 和 `table_to_list` 的顺序可能影响结果。
- `table_to_list` 如果执行两次，可能把已经列表化的内容再次处理。

建议：

补 `shared_pipeline_policy`：

```yaml
shared_post_processing:
  - name: sanitize_text
    order: 10
    idempotent: true
  - name: table_to_list
    order: 20
    idempotent: must_test
```

shared_promotion 实验必须包括：

- 当前分支不双重应用
- 所有分支按新 pipeline 重跑
- P 的幂等测试
- 与已有 shared steps 的顺序测试

### P2：`0 回退` 需要容差，否则会抖动

位置：

- `员工蒸馏器-三选一阈值与shared_promotion.md:76`
- `员工蒸馏器-三选一阈值与shared_promotion.md:78`

问题：

文档要求“0 个分支回退”。原则是对的，但如果行为指标包含文本覆盖率、标题保留率、图片覆盖率等数值，测量会有噪声。

风险：

- 轻微浮动导致 shared_promotion 被反复否决。
- 不同抽取器版本导致结果抖动。

建议：

定义 tolerance：

```text
numeric axis: delta < epsilon 不算回退
categorical axis: 只有违反 branch policy 才算回退
hard gate fail: 永远算回退
```

## 5. 运维层

### 总体判断

这份运维层补得很有必要。它把之前偏“管线设计”的文档往真实可运行系统推进了一步：三进程独立、daemon 断点续接、judge 成本控制、配置默认值、故障降级、密钥与沙箱、可观测性都有覆盖。

但现在的问题是：有些说法还是“设计口号”级别，落到实现会产生歧义。尤其是 `processing_stage` 的排序、Composer 写 `skills/` 的原子性、judge 缓存键、凭证继承、磁盘满和 GC、脱敏与 hook <5ms 的冲突，都需要补成可执行规则。

### P1：`processing_stage < 'composed'` 不能用字符串比较

位置：

- `员工蒸馏器-运维层.md:30`
- `员工蒸馏器-运维层.md:37`
- `员工蒸馏器-运维层.md:41`

问题：

文档用：

```sql
SELECT * FROM candidates
WHERE processing_stage < 'composed' AND lifecycle NOT IN ('archived','deprecated')
```

这在实现里很危险。`processing_stage` 是业务阶段顺序，不是字典序字符串。比如 `classified`、`contract_extracted`、`gate0_done`、`judged` 的字典序不等于管线顺序。

风险：

- daemon 重启后捞错候选，漏处理或重复处理。
- 后续新增阶段时，字符串排序更容易出错。
- 某些已完成阶段可能被误认为未完成，导致重复 compose。

建议：

给阶段显式编号或状态集合，不要比较字符串：

```text
processing_stage:
  discovered: 10
  gate0_done: 20
  replayed: 30
  output_gated: 40
  contract_extracted: 50
  judged: 60
  classified: 70
  composed: 80
```

查询改成：

```sql
WHERE processing_stage_rank < 80
```

或更直白：

```sql
WHERE processing_stage IN (
  'discovered',
  'gate0_done',
  'replayed',
  'output_gated',
  'contract_extracted',
  'judged',
  'classified'
)
```

### P1：Composer 的“git commit 或 SQLite 事务”没有解决跨文件树 + 数据库原子性

位置：

- `员工蒸馏器-运维层.md:50`
- `员工蒸馏器-运维层.md:52`
- `员工蒸馏器-运维层.md:60`

问题：

Composer 同时会改两类东西：

- `skills/` 文件树
- SQLite 里的候选状态、索引、血缘、commit/hash 引用

单独说“git commit 原子”或“SQLite 事务”不够。git 只能保证文件树提交，SQLite 只能保证数据库事务，它们之间不是天然一个事务。

风险：

- 文件已经 commit，但 DB 还停在 `classified`。
- DB 标了 `composed`，但 `skills/` 没有对应 commit。
- 崩溃恢复时不知道该以文件树为准还是以 DB 为准。

建议：

补一个两阶段写入协议：

```text
1. compose 到 staging 目录，不直接改 active skills/
2. 校验 staging 的 manifest / contract / lineage / tests
3. git commit staging -> active，拿到 commit_id
4. SQLite transaction 写入 composed 状态、commit_id、content_hash
5. daemon 启动时做 reconcile：
   - 有 commit 无 DB：补 DB 或标 orphan_commit
   - 有 DB 无 commit：回滚 DB 状态或标 corrupted_candidate
```

关键是 `skills/` 的每个 promoted 版本必须能用 `commit_id + content_hash` 和 SQLite 记录互相校验。

### P1：judge 缓存键太窄，会把过期判断当成命中

位置：

- `员工蒸馏器-运维层.md:87`

问题：

当前写的是按 `(contract_sig_C, contract_sig_S)` 缓存 judge 结果。这只能说明两个契约签名相同，不能说明判断环境相同。

至少还需要进入缓存键或缓存记录：

- `judge_prompt_version`
- `judge_schema_version`
- `judge_model/provider`
- `behavior_signature_schema_version`
- `branch_identity`
- `input_profile`
- `comparison_policy_version`

风险：

- prompt 改了，但仍命中过去的 judge 结果。
- behavior schema 改了，但旧结论继续生效。
- Haiku 和 Sonnet 的判断混在同一个缓存键里。
- 某个输入类型下成立的“同目的/新分支”，被误用到另一个输入类型。

建议：

缓存键改成类似：

```text
judge_cache_key =
  hash(
    contract_sig_C,
    contract_sig_S,
    behavior_sig_C,
    behavior_sig_S,
    branch_identity,
    input_profile,
    judge_prompt_version,
    judge_schema_version,
    comparison_policy_version,
    model_id
  )
```

如果觉得太长，可以用结构化字段落库，再生成 hash。

### P1：“复用 CC 凭证”不能写成一定成立

位置：

- `员工蒸馏器-运维层.md:67`
- `员工蒸馏器-运维层.md:71`
- `员工蒸馏器-运维层.md:83`
- `员工蒸馏器-运维层.md:97`

问题：

文档说 daemon 复用 CC 正在用的 Anthropic key，默认从 `ANTHROPIC_API_KEY` 读。这作为“支持路径”可以，但不能假设 CC 本体一定把可复用 API key 暴露在环境变量里。

风险：

- 用户以为装上就能跑 judge，实际 daemon 拿不到 key。
- CC 的登录态/订阅态和 Anthropic API key 不是同一个东西。
- 把“凭证继承”写死，会导致后续适配别的 agent 或本地模型时很别扭。

建议：

改成：

```text
judge credential resolution:
1. CLI flag / explicit config
2. env: ANTHROPIC_API_KEY
3. provider-specific local secret store
4. disabled/offline judge mode
```

并明确：

- 不保证能直接读取 CC 会话凭证。
- key 永远不进 trace、artifact、报告和 git。
- 日志里只允许记录 provider 与 key fingerprint 后 4 位或 hash 前缀。

### P1：磁盘满时“采集仍可写、丢最旧 trace”不安全

位置：

- `员工蒸馏器-运维层.md:145`

问题：

磁盘满时不能假设“采集仍可写”。恰恰相反，append-only trace 最可能失败。并且“丢最旧 trace”也不一定安全，因为旧 trace 可能已经被 promoted skill 的 lineage、fixture、R_miss、behavior_signature 引用。

风险：

- 采集 quietly drop，但系统以为仍在采集。
- 丢掉仍被引用的 artifact，导致回归、解释、审计断链。
- retention GC 为了腾空间破坏已转正能力的证据链。

建议：

补 `lineage-aware retention`：

```text
禁止 GC：
- promoted skill 引用的 source trace/artifact
- fixture / regression case
- R_miss 样本
- behavior_signature 生成依据
- judge evidence

允许 GC：
- 未被引用的 raw trace
- 已归档且超过保留期的中间缓存
- 可重建的临时 venv / replay workdir
```

磁盘满时处理应改成：

```text
1. 进入 degraded_capture 状态
2. 只写最小 RawToolEvent 或记录 capture_drop_count
3. 触发 lineage-aware GC
4. 仍不足时停止重放/compose，保留前台无感
5. 报告 Capture Drop Rate / Disk Pressure
```

### P1：配置样例又引入了全局 `text_coverage_min = 0.9`

问题：

### P2：hook “不能挂”的说法过强，应该改成“不能反噬前台”

位置：

- `员工蒸馏器-运维层.md:16`
- `员工蒸馏器-运维层.md:20`

问题：

同一行里既写“采集 hook 不能挂”，又写“hook 失败也必须静默退出”。这两个表述有冲突。真实底线不是 hook 永远不失败，而是 hook 失败不能打断 CC，也不能让失败长期不可见。

建议：

改成：

```text
采集 hook 可以失败，但必须：
- 非阻塞
- 静默
- 有带外错误计数
- 有 Capture Drop Rate
- 失败不反向影响工具调用
```

这也和前面技术栈文档里的 hook 带外计数问题一致。

### P2：“采集即脱敏”与 hook <5ms 有冲突，需要分层

位置：

- `员工蒸馏器-运维层.md:154`

问题：

采集时脱敏方向是对的，但如果 hook 在同步路径里做复杂正则、文件扫描、上下文解析，就会破坏 `<5ms` 和“只 append 一行”的无感约束。

建议：

分两层脱敏：

```text
hook fast redaction:
- 只处理 env 中已知 secret 的精确值
- 只处理常见 argv 形态：--token= / --api-key= / Authorization:
- 设置严格耗时上限

daemon deep redaction:
- 对 artifact / output / report 做更完整扫描
- 命中后生成 redaction_report
- 不阻塞前台工具调用
```

也要补一条：脱敏失败时宁可降级保存最小事件，也不要把疑似 secret 写进 artifact。

### P2：默认断网重放会影响依赖安装，需要拆 install 与 run

位置：

- `员工蒸馏器-运维层.md:119`
- `员工蒸馏器-运维层.md:122`
- `员工蒸馏器-运维层.md:155`

问题：

`network = "off"` 对重放确定性和安全是好的，但很多候选需要装依赖。尤其是 `doc2md.py` 这种现实工具，可能涉及 Python 包、系统工具、LibreOffice、OCR 组件等。

风险：

- replay 阶段因为断网装不了依赖，被误判成候选失败。
- 为了跑通 replay 又临时开网，破坏安全边界和可复现性。

建议：

拆成两个阶段：

```text
dependency_resolve/install:
  network: allowlist 或 cached-only
  lockfile required
  产出 dependency_snapshot

replay/run:
  network: off
  read dependency_snapshot
  不访问外网
```

MVP 可以先支持：

- `uv` lock/cache
- 固定 wheel cache
- host capability profile
- 无法满足依赖时标 `deferred_dependency`，不直接判失败

### P2：可观测性缺少队列状态、重试和死信策略

位置：

问题：

现在的指标有队列深度、成本、失败率、断点续接次数，但缺少 job 级生命周期。daemon 是批处理系统，必须知道每个候选卡在哪、重试几次、什么时候不再自动重试。

并给 reports 增加：

- `dead_letter_count`
- `oldest_queued_age`
- `stage_latency_p50/p95`
- `retry_count_by_stage`
- `stuck_jobs`

## 7. 一句话收束

这几份补丁已经把主脊基本立住了。下一步不是再加概念，而是把几个“比较关系”和“运行时边界”定义清楚：什么算同一个分支、什么行为字段可比较、什么失败能进 R_miss、什么 shared 后处理能提级、什么能力才值得暴露成 MCP tool、daemon 挂了怎么续、文件树和 SQLite 怎么一致、哪些证据永远不能被 GC。只要这些规则补硬，v0.4 的“保年轮、不误洗、不乱召回”和“无感运行”就会更稳。
