# 员工蒸馏器 · 相似项目与模块借用盘点

> 目标：整理当前最接近的开源项目、覆盖其中一部分能力的基础设施、以及已经落地的产品，并明确：
> - 哪些能直接借模块
> - 哪些只能借思路
> - 哪些看起来像，但不能替代我们的核心引擎
>
> 日期：2026-06-20

---

## 1. 一句话结论

目前**没有一个现成项目或产品完整覆盖**这套设计。

最接近的是：

- `Yunjue-Agent`：最像“工具会自己长”的研究骨架
- `Letta Code / Context Repositories`：最像“git-backed 长期记忆 + 渐进式披露 + 子代理处理历史”
- `Zep / Graphiti`、`Mem0`：最像“长期记忆 / 图谱 / 检索层”
- `MCP Registry`、`Smithery`、`Composio`：最像“分发、接入、认证、托管层”

但下面这些关键部分，我还没看到现成成品：

- 从真实 trace 抽契约签名
- 用契约/目的做主轴判同
- `new_skill / new_branch / branch_iteration` 三选一分类
- `Composer` 组织变体而不是 `Merger` 消灭变体
- 保年轮、保伤疤、保 lineage 的工具生长模型

## 2. 最像的开源项目

### 2.1 Yunjue-Agent

定位：

- 最接近“工具演化引擎”的项目
- 官方实现明确强调 self-evolving agent、zero-start、可复现实验和日志数据

最值得借的地方：

- `retrieve -> decide -> create` 三段式
- `reuse-before-create`
- batch absorb / evolution
- 执行级二元反馈
- warm-start 评估

不该照抄的地方：

- 它把变体更多当噪声，合并倾向做 canonical 化
- 功能等价更多依赖 LLM 读描述/代码猜
- 不擅长“保住边缘处理年轮”

适合借用的模块：

- `manager / retrieval loop`
- `R_miss` 风格的失败记忆
- `batch evolution scheduler`
- `aggregator` 的流程骨架

不适合作为现成替代的模块：

- `merger`
- 直接的功能等价判定逻辑

来源：

- [Yunjue-Agent GitHub](https://github.com/YunjueTech/Yunjue-Agent)
- [Tech Report](https://arxiv.org/html/2601.18226v1)

### 2.2 Letta Code / Context Repositories

定位：

- 最接近“长期 agent 记忆 + git-backed context 仓库”的落地形态

最值得借的地方：

- context repositories
- git-backed versioning
- progressive memory disclosure
- subagents 处理历史和上下文
- memory 作为本地文件系统来管理

它强的不是工具蒸馏，而是：

- 如何让 agent 的长期上下文可版本化
- 如何让记忆可以被 agent 自己读写
- 如何让多代理在上下文层并发工作

适合借用的模块：

- `memory repository` 的存储思想
- `git-backed lineage / versioning`
- `progressive disclosure`
- `subagent-friendly context handling`

不适合作为现成替代的模块：

- 契约引擎
- 三选一分类
- Composer

来源：

- [Letta GitHub](https://github.com/letta-ai/letta)
- [Letta Code GitHub](https://github.com/letta-ai/letta-code)
- [Context Repositories blog](https://www.letta.com/blog/context-repositories/)
- [Letta Code memory docs](https://docs.letta.com/letta-code/memory/)

## 3. 覆盖半边功能的基础设施

### 3.1 Zep / Graphiti

定位：

- 长期记忆、时序图谱、上下文图检索

最值得借的地方：

- temporal context graph
- evolving relationships over time
- graph + vector + full-text 的混合检索
- provenance / timeline 的表达方式

适合借用的模块：

- `memory graph`
- `historical retrieval`
- `context provenance`

不适合替代的模块：

- 工具蒸馏
- 分支生长
- Composer

来源：

- [Graphiti overview](https://help.getzep.com/graphiti/getting-started/overview)
- [Graphiti product page](https://www.getzep.com/platform/graphiti/)

### 3.2 Mem0

定位：

- 通用 memory layer

最值得借的地方：

- user / session / agent memory 分层
- add / search / update / delete 这类 memory API 语义
- “记忆不必等于上下文全文”的产品抽象

适合借用的模块：

- `memory scope model`
- `memory CRUD`
- `metadata filter` 思路

不适合替代的模块：

- trace -> contract extraction
- tool growth model
- branch / iteration 管线

来源：

- [Mem0 docs intro](https://docs.mem0.ai/introduction)
- [Memory Types](https://docs.mem0.ai/core-concepts/memory-types)
- [Platform overview](https://docs.mem0.ai/platform/overview)

## 4. 分发、接入、认证层

- 官方 centralized metadata repository

最值得借的地方：

- 作为公开分发层的模型
- metadata registry 的角色定义
- “registry 不等于 host runtime”的边界

适合借用的模块：

- `public metadata registry`
- `server/package metadata shape`

不适合替代的模块：

- 私有能力库
- 契约引擎

## 5. 已落地产品

### 5.1 Devin

定位：

- 产品化最强的 coding agent 之一
- 已经在强调 “learns your codebase & picks up tribal knowledge”

它像什么：

- 强执行代理
- 强知识吸收产品
- 团队协作型 coding agent

适合借的不是代码，而是产品判断：

- 用户愿意为“会学、会记、会复用”的 coding agent 付费
- “tribal knowledge” 是真实痛点
- 长期知识不是可有可无的装饰层

不适合替代的模块：

- 没有现成开源引擎给你借
- 也不是围绕“trace -> contract -> branch growth”来公开设计的

来源：

- [Devin docs intro](https://docs.devin.ai/get-started/devin-intro)
- [Devin product page](https://devin.ai/)
- [Cognition homepage](https://cognition.ai/)

### 5.2 OpenHands

定位：

- 更像“developer control center / automation canvas / agent orchestration”

最值得借的地方：

- always-on engineering team 的产品外壳
- 控制中心式 orchestration 体验
- 多 agent / automation 的宿主形态

适合借用的模块：

- `agent orchestration shell`
- `control center UX` 思路
- `task decomposition surface`

不适合替代的模块：

- 契约引擎
- 能力沉淀模型
- 年轮式工具生长

来源：

## 6. 模块借用表

| 我们的模块 | 最值得借的项目/产品 | 借什么 | 不够的地方 |
|---|---|---|---|
| `retrieve -> decide -> create` 主循环 | Yunjue-Agent | manager / retrieval loop / `R_miss` / batch evolution | 不理解“保年轮” |
| `Replay Gate` / 执行反馈 | Yunjue-Agent | pass/fail 的客观反馈链 | 还不够覆盖属性型 Output Gate |
| `memory repository` / 上下文仓库 | Letta Code | git-backed context repositories / progressive disclosure | 不提供契约级工具生长 |
| `lineage / versioning` | Letta Code | git history、subagent 并发上下文 | 不是 branch / iteration 专用模型 |
| `long-term memory graph` | Graphiti / Zep | temporal graph、timeline、hybrid retrieval | 不处理可执行工具分支 |
| `memory scope` | Mem0 | user / session / agent scope | 不处理 trace 蒸馏 |
| `public registry` | MCP Registry | metadata registry 模型 | 不做内部知识与质量 |
| `marketplace / discovery` | Smithery | registry 搜索、CLI、发布流程 | 不做能力生长 |
| `managed auth / hosted MCP` | Composio | auth、gateway、hosted connector | 不做契约抽取与分类 |
| `orchestration shell` | OpenHands | 控制中心 / 自动化外壳 | 不提供契约引擎 |
| `product proof` | Devin | “会学的 coding agent” 的市场教育 | 无法直接借实现 |

## 7. 哪些必须自己做

这是现在最值得明确的一段。

即使把上面这些项目全拼起来，下面这几个模块仍然要自己造：

### 7.1 契约引擎

原因：

- 没有现成项目把“真实观测 I/O”作为主锚来抽契约
- 大多数项目不是从跨项目 trace 反推能力

至少要自己做：

- `contract_signature`
- `branch_identity`
- `behavior_signature`

### 7.2 三选一分类器

原因：

- 现成系统大多只做“复用 / 新建”二选一
- 少有系统显式区分：
  - `new_skill`
  - `same_purpose_new_branch`
  - `branch_iteration`

### 7.3 Composer

原因：

- Yunjue 的 `Merger` 倾向 canonicalize
- 你这里的核心是“组织变体、保留年轮、提升 shared post-processing”

### 7.4 年轮与回归模型

原因：

- 真实成熟工具的价值在边缘修补、健壮性和输出手艺
- 这部分不能被去特化逻辑洗掉

至少要自己做：

- `iteration_log`
- `shared_promotion`
- cross-branch regression

### 7.5 warm-start 回灌到宿主

原因：

- 很多系统有记忆，但不一定能在“模型准备重搓某目的前”精准把已有能力捞出来

至少要自己做：

- 目的级召回
- `R_miss` 缩作用域
- L1/L2 渐进式注入策略

## 8. 推荐借用顺序

为了避免一次借太多，建议按这个顺序借：

1. **先借 Yunjue 的流程骨架**
   借主循环、批量吸收、`R_miss` 思路

2. **再借 Letta 的上下文仓库思想**
   借 git-backed memory、progressive disclosure、subagent 处理历史

3. **然后补 Graphiti / Mem0 的记忆表达**
   只借长期记忆和图谱表达，不要把它们抬成主引擎

4. **最后接 MCP Registry / Smithery / Composio**
   作为发布、分发、认证、托管层

这样做的好处是：

- 先把发动机造出来
- 再把仓库和分发层补齐
- 不会一开始就陷进“平台工程”里

---

## 9. 一句话判断

现在最像你的不是一个现成产品，而是一组可拼装的能力层：

- `Yunjue` 提供“会长”的骨架
- `Letta` 提供“记得住”的仓库
- `Graphiti / Mem0` 提供“记忆怎么组织”
- `MCP Registry / Smithery / Composio` 提供“怎么发、怎么接、怎么管”

而真正让这件事成为你自己的东西的，是中间那段还没人替你做完的引擎：
**trace -> contract -> purpose -> branch/iteration -> Composer -> warm-start**
