# 员工蒸馏器 · 观测与审查层审核意见

> 审阅对象：`员工蒸馏器-观测与审查层.md`
>
> 参考基准：
> - `员工蒸馏器-设计文档-v0.4.md`
> - `员工蒸馏器-运维层.md`
> - `forcodex/员工蒸馏器-三份补丁文档问题清单.md`
>
> 结论：方向是对的。它补上了“人怎么看库、怎么看调用效果、怎么纠偏”的入口，而且坚持 pull 模式，和 v0.4 的无感原则一致。但现在有几个表达过于绝对，尤其是“永不 push”“待审不能阻塞主流程”“ambiguous 自动选 active”“疑似误合并默认保持合并态”。这些如果不收紧，会在 promoted/exposed、团队共享、安全风险、误合并恢复时出问题。
>
> 日期：2026-06-20

---

## 1. 总体判断

这份文档解决的是之前确实缺的一层：系统不能只在后台沉淀，还要让人能 pull 出来查看、判断和纠偏。MVP 用 CLI + Obsidian 只读视图也合理，不必一开始做复杂 dashboard。

但它还需要补三个边界：

1. **pull 不等于永远没有告警**：不能打扰前台工作，但严重运维/安全/数据丢失风险需要低噪声状态提示或 health 标记。
2. **待审不阻塞采集/后台处理，不代表不阻塞晋升/暴露**：进入 MCP 一等工具、团队共享、shared 后处理提升，必须有更高门槛。
3. **人工审核不是一个 loose action，而是一条可追溯决策流**：要有 ReviewItem schema、证据包、决策类型、落库规则、回滚规则。

## 2. P1 问题

### P1：`永不 push` 写得太绝对，会漏掉严重健康/安全状态

位置：

- `员工蒸馏器-观测与审查层.md:4`
- `员工蒸馏器-观测与审查层.md:26`
- `员工蒸馏器-观测与审查层.md:139`

问题：

“审查是 pull，不是 push”这个方向对，尤其不能打断 CC 前台会话。但文档写成“系统永不主动 push 任何审查请求”，会把两类事情混在一起：

- 普通审查：ambiguous、Path-B pin、误合并复核，这些可以 pull。
- 严重状态：磁盘满、采集 drop、疑似 secret 泄漏、SQLite 损坏、MCP 暴露异常、团队共享发布失败，这些不能只等人哪天想起来查。

风险：

- 采集已经大量丢失，但用户长期不知道。
- secret 可能进入 artifact/report，但没有显著标记。
- 团队模式下关键发布状态没人处理，能力库长期处于不一致状态。

建议：

把原则改成：

```text
普通审查 pull-only；
严重健康/安全状态不打断前台，但允许低噪声暴露：
- health status
- CLI banner
- reports/health.json
- Obsidian dashboard note
- 可选桌面通知/CI fail，仅团队模式开启
```

也就是“不弹审查待办”，但不能“不报告事故”。

### P1：`待审不能阻塞主流程` 需要拆成采集/处理/晋升/暴露四种流程

位置：

- `员工蒸馏器-观测与审查层.md:30`
- `员工蒸馏器-观测与审查层.md:32`
- `员工蒸馏器-观测与审查层.md:35`
- `员工蒸馏器-观测与审查层.md:36`

问题：

“待审不能阻塞主流程”作为无感原则是对的，但“主流程”太宽了。不同流程的默认行为不一样：

- 采集流程不能被审查阻塞。
- daemon 分析流程可以继续跑。
- promoted 晋升可以保守等待证据或人审。
- exposed/MCP 一等工具暴露、团队共享、shared 后处理提升，应该允许被审查阻塞。

风险：

- 候选还没审清楚就进入用户可见工具面。
- shared 后处理影响多个分支，却因为“不能阻塞”被自动应用。
- 团队共享发布绕过人工确认。

建议：

补一张阻塞矩阵：

| 阶段 | 待审是否阻塞 | 默认行为 |
|---|---|---|
| capture | 不阻塞 | 继续采集，记录 review_flag |
| daemon enrichment | 不阻塞 | 继续产出 evidence |
| verified | 通常不阻塞 | 可进入 verified/candidate |
| promoted | 个人模式可自动，团队模式可阻塞 | 取决于 policy |
| exposed as MCP tool | 应可阻塞 | 未审只可通过 search/run 间接调用，不进一等工具列表 |
| shared_post_processing | 应可阻塞 | 未审不提升到父级 |
| team publish | 应阻塞 | 未审不发布 |

一句话：审查不该卡住“观察和分析”，但可以卡住“影响别人和影响前台工具面”的动作。

### P1：ambiguous 默认“并列保留 + active 自动选”容易污染正式能力

位置：

- `员工蒸馏器-观测与审查层.md:32`

问题：

文档说 ambiguous 默认并列保留 `retained_impls`，`active` 按聚合分自动选。并列保留是对的，不丢年轮；但“active 自动选”危险，尤其当这个 active 会被 MCP 调用或 warm-start 推荐时。

风险：

- judge 已经判不清迭代/重复，系统却仍自动切 active。
- 新实现可能只是绕过失败，输出质量退化。
- 旧稳定分支被未审实现替换，后续任务开始误用。

建议：

改成两层 active：

```text
stable_active:
  当前正式对外使用的实现，人审前不变

provisional_candidate:
  daemon 可在沙箱里继续评估的新实现
  可以参与 shadow run
  不进入 MCP exposed，不替换 stable_active
```

ambiguous 默认行为应是：

```text
保留 C 为 retained/provisional；
旧 B 继续 stable_active；
继续收集 fixture / reuse / R_miss；
人审或证据足够后再 promote-impl。
```

### P1：疑似误合并默认“保持合并态”不够安全

位置：

- `员工蒸馏器-观测与审查层.md:36`

问题：

文档写“疑似误合并：保持合并态 + 标记 review_flag”。如果这个合并已经影响召回、active 分支或 shared 后处理，继续保持合并态可能会扩大污染。

风险：

- 错误父能力继续被 warm-start 命中。
- shared 后处理继续作用于不该作用的分支。
- 被误合并的能力在用户看见前已经污染 usage/quality 统计。

建议：

疑似误合并默认改成“冻结影响面”，而不是简单保持合并态：

```text
suspected_mismerge:
  freeze_new_exposure: true
  freeze_shared_promotion: true
  stable_active: pre_merge_active
  keep_merged_snapshot: true
  allow_explicit_run_by_id: true
  require_review_for_warmstart: true
```

也就是：快照保留、可回退，但不要继续扩大对外影响。

### P1：审查队列类型太少，漏掉 promoted/exposed 和安全类审查

位置：

- `员工蒸馏器-观测与审查层.md:87`
- `员工蒸馏器-观测与审查层.md:90`
- `员工蒸馏器-观测与审查层.md:91`

问题：

现在 `distiller pending` 只列了：

- ambiguous
- path-b
- review

这不够。结合 v0.4 和前面问题清单，至少还需要：

- `exposure_review`：promoted -> exposed/MCP 一等工具
- `shared_promotion_review`：分支后处理提升到父级
- `security_review`：疑似 secret、硬编码路径、危险副作用
- `dependency_review`：系统依赖、网络依赖、host capability
- `team_publish_review`：个人能力发布到团队共享池
- `gc_review`：准备删除/归档被引用不明的 artifact
- `schema_migration_review`：迁移前后不一致或需要人工确认

建议：

`pending` 至少按类型和风险分组：

```text
distiller pending
  --type ambiguous|path-b|mismerge|exposure|shared|security|dependency|team-publish|gc
  --risk p1|p2|p3
  --scope personal|team
```

### P1：审查包没有正式 schema，CC 实现时容易变成散文报告

位置：

- `员工蒸馏器-观测与审查层.md:94`

问题：

文档说“每项附齐决策所需信息”，但没有定义必须包含哪些字段。这个很关键，因为人工审核要避免“人重新读项目”。

建议：

补 `ReviewItem` schema：

```yaml
review_item:
  id: review_2026_06_20_001
  type: ambiguous_iteration
  risk: P1
  blocking_scope: [exposure, shared_promotion]
  candidate_id: candidate_x
  target_skill: doc-to-markdown
  target_branch: xlsx_table
  system_recommendation: keep_both
  alternatives:
    - approve_iteration
    - approve_new_branch
    - reject_duplicate
    - defer_more_evidence
  gate_summary:
    gate0: pass
    replay: pass
    output_gate: pass
    contract_gate: pass
  evidence_refs:
    - artifacts/...
    - reports/...
    - fixtures/...
  comparison:
    baseline: markitdown
    behavior_signature_diff: ...
    R_miss_result: ...
  risk_summary:
    - system_dependency
    - possible_regression
  reversible_action:
    rollback_ref: commit_id
```

CLI `distiller show-review <id>` 和 Obsidian review note 都应该从这个结构生成。

## 3. P2 问题

### P2：审查动作不够类型化，`pin/resolve/deprecate` 会变成万能按钮

位置：

- `员工蒸馏器-观测与审查层.md:96`
- `员工蒸馏器-观测与审查层.md:99`
- `员工蒸馏器-观测与审查层.md:100`
- `员工蒸馏器-观测与审查层.md:101`
- `员工蒸馏器-观测与审查层.md:102`
- `员工蒸馏器-观测与审查层.md:103`
- `员工蒸馏器-观测与审查层.md:104`

问题：

现在的动作有：

```text
pin / resolve --iteration / resolve --keep-both / deprecate / unmerge / promote-impl
```

但没有覆盖新能力、新分支、拒绝、延期、暴露、取消暴露、团队发布等动作。`pin` 也太宽，会把“高价值破格晋升”和“人工确认”混在一起。

建议动作集改成更明确：

```text
approve-new-skill <candidate>
approve-new-branch <candidate> --skill <skill> --branch <branch>
approve-iteration <candidate> --skill <skill> --branch <branch>
keep-fallback <candidate> --skill <skill> --branch <branch>
promote-shared <review_id> --step <name>
reject <candidate> --reason <reason>
defer <review_id> --need <more_fixtures|more_usage|security_review>
pin-path-b <candidate> --reason <reason>
expose <skill> --mode mcp-tool
unexpose <skill>
rollback-review <review_id>
```

每个动作都必须要求 `reason`，并写入 lineage。

### P2：usage 数据不应该主要写进 `iteration_log`

位置：

- `员工蒸馏器-观测与审查层.md:68`
- `员工蒸馏器-观测与审查层.md:70`

问题：

文档说调用效果来源是“迭代日志”。但 `iteration_log` 应该记录能力变更：分支新增、就地迭代、shared 后处理、人工审查、回滚。日常调用、成功/失败、warm-start 命中如果都塞进 iteration_log，会让 manifest 变重，也会污染“年轮”。

建议：

拆开：

```text
iteration_log:
  记录能力如何演化

usage_events:
  记录每次显式调用/成功/失败

warmstart_events:
  记录召回、注入、命中、未命中

failure_cases / R_miss:
  记录值得回归的失败样本

quality_rollup:
  从 usage_events 聚合出的成功率、复用数、近期趋势
```

CLI 展示可以聚合这些数据，但不要把所有事件塞回 manifest。

### P2：Obsidian 视图要明确只读与脱敏边界

位置：

- `员工蒸馏器-观测与审查层.md:41`
- `员工蒸馏器-观测与审查层.md:45`
- `员工蒸馏器-观测与审查层.md:48`
- `员工蒸馏器-观测与审查层.md:50`
- `员工蒸馏器-观测与审查层.md:51`

问题：

“直接 Obsidian over `skills/`”很轻，但要小心两个问题：

1. 用户可能在 Obsidian 里误编辑 manifest，和 daemon/git 写入冲突。
2. `lineage` / `snapshot_refs` / failure 样本可能带敏感路径、项目名、客户名、trace 片段。

建议：

MVP 可以不直接打开真实 `skills/`，而是生成一个只读视图：

```text
views/obsidian/
  skills/
    doc-to-markdown.md     # L1/L2 摘要 + 脱敏 lineage 摘要
  reviews/
    review_*.md
  health.md
```

真实 `skills/` 仍由 daemon/CLI 写。Obsidian 视图只作为 projection，可重建、可丢弃。

如果坚持直接 over `skills/`，也要写明：

```text
Obsidian edits are ignored/forbidden；
任何人工动作必须走 distiller CLI；
L4 原始证据默认不展开，只显示 evidence_ref。
```

### P2：人工写操作需要走同一套原子写和 reconcile

位置：

- `员工蒸馏器-观测与审查层.md:107`
- `员工蒸馏器-观测与审查层.md:120`

问题：

文档说“所有动作写 lineage”，但没说怎么写。人工动作会改 SQLite、skill manifest、git commit、可能还改 MCP exposure index。它和 Composer 一样有跨文件树 + DB 原子性问题。

建议：

所有审查动作都走 `ReviewAction transaction`：

```text
1. validate review_item still current
2. write staging manifest / lineage patch
3. run required regression if action affects active/exposed/shared
4. git commit with review_action_id
5. SQLite transaction write decision + commit_id
6. update index/exposure after commit
7. on daemon restart reconcile review_action_id
```

不要允许人直接改 markdown manifest 当作正式决策。

### P2：`distiller pending` 需要状态生命周期，否则队列会变成垃圾堆

位置：

- `员工蒸馏器-观测与审查层.md:85`
- `员工蒸馏器-观测与审查层.md:94`

问题：

文档定义了 pending 入口，但没有定义 review item 自己的状态。

建议：

补：

```text
review_state:
  open
  acknowledged
  resolved
  deferred
  superseded
  expired
  archived
```

并定义：

- 什么情况下自动 superseded：新证据已经让 ambiguous 自动变清楚。
- 什么情况下 expired：候选长期不用、已 deprecated。
- deferred 需要 `next_check_at` 或 `need_more_evidence`。

### P2：`unmerge <skill>` 太粗，需要 preview + 作用域

位置：

- `员工蒸馏器-观测与审查层.md:103`

问题：

误合并可能发生在不同层级：

- 父能力合错
- 分支挂错
- iteration 覆盖错
- shared_post_processing 提升错

一个 `unmerge <skill>` 太粗，容易拆过头。

建议：

拆成：

```text
distiller unmerge preview <review_id>
distiller unmerge apply <review_id> --scope parent|branch|iteration|shared-step
```

apply 前必须展示：

- 会恢复哪些 commit/manifest
- 会影响哪些 exposed tool
- 会影响哪些 fixtures/quality stats
- 回滚后要跑哪些 regression

### P2：前台 exposure 和审查层的关系还没写清

位置：

- `员工蒸馏器-观测与审查层.md:120`
- `员工蒸馏器-观测与审查层.md:126`
- `员工蒸馏器-观测与审查层.md:130`

问题：

文档说审查层读 `SQLite + skills/ + reports/`，MVP 做 `ls/show/pending/usage/failures/pin/resolve/deprecate`。但它还没定义：

- 什么是用户前台可见：CLI 可见、Obsidian 可见、MCP 可见是三回事。
- 什么能力可以被 MCP search 找到。
- 什么能力可以变成一等 MCP tool。
- 审查动作是否影响 exposure。

建议：

补一层 exposure 状态：

```text
visibility:
  hidden          # 只在内部候选库
  reviewable      # pending 可见
  searchable      # 可被 distiller.search 找到
  invokable_by_id # 可显式 run
  mcp_exposed     # 一等 MCP tool
  team_published  # 团队共享
```

并明确：`promoted != exposed`。promoted 是能力库转正，exposed 是前台工具面可见。

## 5. 建议给 CC 的修改顺序

### 第一优先级

1. 把 `永不 push` 改成“普通审查 pull-only；严重健康/安全状态低噪声暴露”。
2. 补“待审阻塞矩阵”，明确 capture/daemon 不阻塞，但 exposed/team/shared 可以阻塞。
3. 修改 ambiguous 默认策略：未审实现只能 provisional/shadow，不自动替换 `stable_active`。
4. 修改疑似误合并默认策略：冻结对外影响面，保留回退快照。
5. 扩充 pending 类型，至少加入 exposure/shared/security/dependency/team-publish/gc。
6. 定义 `ReviewItem` schema。

### 第二优先级

1. 类型化审查动作，不要只靠 `pin/resolve/deprecate`。
2. 拆 `iteration_log` 与 `usage_events/warmstart_events/quality_rollup`。
3. 明确 Obsidian 只读与脱敏边界，最好生成 `views/obsidian/` 投影视图。
4. 人工动作走 `ReviewAction transaction`，和 Composer 一样解决文件树 + SQLite 一致性。
5. 给 review item 增加状态生命周期。
6. 补 `visibility/exposure` 状态，明确 `promoted != exposed`。

### 第三优先级

1. 修正文档中 v0.4 §5.5 的引用。
2. 给 MVP CLI 补最小输出样例。
3. 把 `unmerge` 拆成 preview/apply，并要求作用域。

## 6. 一句话收束

这份“观测与审查层”的方向很对：它让系统从无感黑箱变成可查、可纠偏的能力库。但要避免把 pull 模式绝对化。更准确的边界应该是：**普通审查不打扰前台，严重状态必须可见；待审不阻塞采集和分析，但可以阻塞晋升、暴露、共享和高风险修改；人工动作必须结构化、可追溯、可回滚。**
