# 员工蒸馏器 · 完整设计文档

> 一个在 agent 运行过程中**无感**沉淀可复用能力(工具/技能),跨项目记忆、递归合并、并支持团队共享的系统。
> 版本:v0.1 草案 · 日期:2026-06-20

---

## 0. 一句话定义

在你日常使用 agent(Claude Code / Codex / Hermes)的过程中,系统在后台自动观察执行轨迹,把**重复出现、可验证、可泛化**的程序类能力蒸馏成最小可复用单元,存进跨项目的本地库,递归合并相似项,并以各家 agent 的**原生形式**(MCP / SKILL.md)重新提供给你和你的团队。

---

## 1. 需求规格(源自原始需求文档)

### 1.1 目标
- 个人或团队使用;在使用 agent 时**无感**地沉淀可复用能力。
- 记录所有项目中重复使用的代码、提示词,或由提示词生成的高频代码。

### 1.2 功能要点
1. 使用 agent 时识别可复用的 tool/skill(**主要是程序类**,如各类格式转 md),自动入库。
2. **跨项目**记忆与调用,体验等同原生 skill/tool。
3. 生成物不稳定、会有相似工具(doc→md / pdf→md / 含图文本→md),需要**递归合并**。
4. 按**最小可泛化单元**记录,而非整条长链(例:视频→文本→脚本→视频 工作流里,沉淀的是通用的"大纲生成",而非整条链)。
5. **远程共享池**:团队成员流程中的工具都能沉淀与合并。

### 1.3 五项标准要求(原文"要求")
1. 可入库技能的**评估标准**。
2. **合并标准**。
3. **记录与检索方式**。
4. 记录标准、**唤起标准**、使用方式、迭代记录。
5. **渐进式披露**的库,不同阶段使用不同信息(如合并时不需要唤起标准)。

### 1.4 本轮确认的两个增补需求
- **A. 限定程序类以最大限度消灭人工审核**:用"可执行 + 可验证"把语义判断转成测试通过判断,人审从关键路径降级为异步兜底。
- **B. 优先适配三家主流 agent**:Claude Code(CC)、Codex、Hermes(NousResearch/hermes-agent)。

## 2. 现有产品调研(为什么要自己做)

市场分三层,每层只覆盖需求的一部分,**没有产品把它们连起来**。

| 层 | 代表产品 | 已做到 | 缺口(对本需求) | 可复用的零件 |
|---|---|---|---|---|
| 自进化 agent / 技能库 | Voyager、SkillOS、MUSE-Autoskill、Yunjue Agent、EvoAgentX、Devin | 成功代码即技能、验证后入库、embedding 检索 | 全是**单 agent 内闭环**;多为研究原型(EvoAgentX 唯一可跑);无跨 agent、无团队池 | 蒸馏范式、技能生命周期、批量聚类合并(Yunjue) |
| Agent 记忆平台 | Letta(MemGPT)、Mem0、Zep、Cognee | 生产可用,成熟的事实/情景记忆 + 检索 | "procedural memory" 都只是**写进 prompt 的行为规则**,无人把流程蒸馏成**可执行工具** | 记忆合并/去重(Mem0)、分层记忆与自主写入(Letta)、bitemporal 检索(Zep) |
| 工具/技能市场 | 官方 MCP Registry(已发布,9600+ server)、Smithery、Skills.sh、Composio | 分发已有工具;MCP 成事实标准 | **纯人工发布+下载,零自动蒸馏**;缺运行时质量信号 | **MCP 协议 + 官方 Registry 直接复用作分发层** |

### 关键结论
1. **没有现成产品可直接用** —— "自动蒸馏 + 最小单元 + 跨 agent + 团队池" 是市场空白。
2. **能抄的是零件,不是整体** —— 蒸馏抄 Voyager/Yunjue,合并去重抄 Mem0,分发层直接用 MCP Registry,不要自造。
3. **天然差异化 = 运行时质量信号** —— 所有市场都缺"这个工具在真实任务里成功率多少",而蒸馏器从 trace 里天生拥有该数据。应作为核心卖点。

## 3. 核心设计原则

1. **程序类优先**:MVP 只沉淀可执行工具(可验证 → 可自动门禁)。提示词类放第二阶段。
2. **统计触发,而非语义判断**:不在生成当下判断"是否通用",而是看复用频次 + 跨项目复现。
3. **最小单元**:按输入/输出解耦的最小可泛化节点沉淀,不存整条长链。
4. **可回退**:任何合并都保留拆分能力;任何自动决策都可被异步审查推翻。
5. **一处管线,多处适配**:采集面每家一个薄 adapter → 统一 trace schema → 核心管线只写一遍 → 服务面以 MCP 为主通用注入。
6. **渐进式披露**:库分层(元数据 / 正文 / 资源 / 治理),不同阶段只加载所需层。

## 4. 整体架构

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ Claude Code │   │   Codex     │   │   Hermes    │   ← 宿主 agent
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │ hooks/          │ JSONL/OTel      │ hook/
       │ transcript      │ session         │ learning-loop
       ▼                 ▼                 ▼
┌───────────────────────────────────────────────────┐
│  采集 Adapter(每家一个,薄)→ 归一化为统一事件     │
└───────────────────────┬───────────────────────────┘
                        ▼  统一 Trace Schema(ToolCallEvent)
┌───────────────────────────────────────────────────┐
│                   核心管线(写一遍)                │
│  ① 候选提取  ② 评估入库  ③ 粒度归一(最小单元)    │
│  ④ 递归合并  ⑤ 索引     ⑥ 召回    ⑦ 迭代反馈     │
└───────────────────────┬───────────────────────────┘
                        ▼
┌───────────────────────────────────────────────────┐
│        技能库(渐进式分层 + 测试样本 + 索引)       │
└───────┬───────────────────────────────┬───────────┘
        ▼ 服务 Adapter                   ▼ 同步
┌───────────────────────┐     ┌───────────────────────┐
│  MCP server(三家通吃) │     │  团队远程共享池        │
│  + SKILL.md 导出(CC/  │     │  (推送/拉取/合并/治理) │
│    Hermes 原生)       │     └───────────────────────┘
└───────────────────────┘
```

### 七步管线
1. **候选提取**:从统一事件流里切出"被生成且被调用"的代码块 / 工具调用 / 高频提示词。
2. **评估入库**:按 §5.1 评分,过阈值才进库;首次只记为"候选",达到复用频次才转正。
3. **粒度归一**:按 §5.2 拆到最小可泛化单元;长链拆成可独立复用的节点。
4. **递归合并**:按 §5.3 与库内相似项聚类、吸收/合并,保留可回退。
5. **索引**:写入渐进式元数据 + 向量索引 + 触发条件。
6. **召回**:下次任务按唤起标准(§5.4)命中,以 MCP/SKILL 原生形式注入。
7. **迭代反馈**:记录使用结果(成功率/被合并/被淘汰),反哺评分(§5.5)。

## 5. 五套标准(对应原文五项要求)

### 5.1 入库评估标准(可执行 → 可自动)
一个候选要转正入库,需同时满足:

| 维度 | 信号 | 阈值(可调) | 自动? |
|---|---|---|---|
| **复用性** | 跨 ≥N 次会话/项目被实际调用 | N≥3 | ✅ |
| **可验证性** | 至少 1 个成功调用样本能作为回归测试跑通 | ≥1 | ✅ |
| **确定性** | 相同输入产出稳定(无随机/无未声明副作用) | 通过 | ✅ AST 检查 |
| **可泛化性** | 输入/输出与具体项目解耦(无硬编码路径/密钥) | 通过 | ✅ 静态扫描 |
| **自包含** | 依赖可声明、可安装 | 通过 | ✅ |

> 评分 = 加权和;高于"入库线"自动转正,介于"候选线"与"入库线"之间继续观察,低于候选线丢弃。
> **人审仅作异步抽查**,不阻塞入库。

### 5.2 最小单元 / 粒度判定标准
目标:沉淀"大纲生成"这种通用节点,而非整条"视频→…→视频"链。

判定一个节点是否为可独立沉淀的最小单元:
1. **接口解耦**:输入/输出类型明确,不依赖上游的内部状态(只吃标准输入)。
2. **纯度**:无未声明外部副作用(AST/数据流分析可判)。
3. **共享度**:被 ≥2 条不同长链复用 → 强信号说明它是通用节点。
4. **不可再分**:再拆下去就失去独立语义(拆出来无法单独验证)。

> 长链处理:拆成 DAG,对每个节点独立跑 5.1。**只沉淀通过的节点,不沉淀整条链**(链本身可作为"工作流模板"存到第二层,非核心库)。
> 边界情况进异步人审队列(粒度判定是少数保留人审的环节之一)。

### 5.3 合并标准(递归 / 可回退)
处理 doc→md / pdf→md / 含图文本→md 这类相似工具。

- **触发**:新工具入库时,与库内做语义聚类(embedding 相似度 > 阈值进入候选合并)。
- **安全判据(自动)**:把候选两方的**测试样本集求并集**,对"合并后的带参数通用工具"全部跑通 → 合并安全;否则保留为独立工具。
- **合并形态**:优先合成"带参数/带 dispatch 的通用工具"(如 `to_md(source, type)`),而非删除特化版本。
- **递归**:合并产物再次进入聚类,直至收敛(Yunjue 的批量吸收思路)。
- **可回退**:保留合并前快照与血缘(lineage);后续若某输入暴露分叉,自动拆回。
- **残留风险**:测试集相同 ≠ 语义等价。缓解=保守阈值 + 持续累积样本 + 异步抽查。

### 5.4 记录 / 检索 / 唤起标准
- **记录**:每个技能一个目录,含 manifest(元数据)+ 实现 + 测试样本 + 血缘 + 迭代日志(schema 见 §7)。
- **检索**:向量检索(描述 embedding)+ 结构过滤(输入/输出类型、标签)+ 运行时质量排序(成功率)。
- **唤起(召回触发)**:
  - 渐进式 —— 先只把**元数据层**(name + 何时使用 + 输入输出签名)注入模型上下文,由模型决定是否展开。
  - 命中条件具体化,避免污染:触发器描述"在什么任务/什么输入类型下用"。
  - 召回错误的代价 > 漏召回 → 阈值偏保守。

### 5.5 迭代记录标准
- 每次调用落一条:输入摘要、输出、成功/失败、宿主 agent、耗时。
- 成功样本自动并入回归测试集(让 5.1/5.3 越来越准)。
- 维护滚动质量分(成功率、最近使用、被合并/被取代)。
- 长期不用或成功率持续走低 → 自动降级/归档。

## 6. 三家 Agent 适配方案

适配分两面,难度差很大:**采集面**(无感捕获,每家不同,难)与**服务面**(原生注入,MCP 通用,易)。

### 6.1 服务面(通用,先定标准)
- **主通道:MCP server** —— 把整个技能库暴露成一个 MCP server,三家(CC/Codex/Hermes)都吃 MCP,**一处实现处处可用**。
- **原生导出:SKILL.md** —— CC 与 Hermes 都用 SKILL.md 格式,额外导出一份,体验更原生、天然支持渐进披露。
- **可选:发布到官方 MCP Registry** —— 团队池可借其分发。

### 6.2 采集面(每家一个薄 adapter)

| Agent | 采集入口 | 难度 | 备注 |
|---|---|---|---|
| **Claude Code** | hooks(PostToolUse 等)+ 会话 transcript | 🟢 低 | 一等公民;开发-测试闭环最快;**首选起点** |
| **Codex** | 结构化 JSONL session 存档 + OTel 导出(`~/.codex/log/`) | 🟢 低 | 采集面最干净(结构化),最适合验证统一 schema 的抽象 |
| **Hermes** | 开源可 hook;但自带 learning loop + 持久记忆 | 🟡 中 | 功能重叠,需先确认其沉淀粒度,决定**共存 or 接管**其 learning loop |

### 6.3 统一 Trace Schema 的价值
各家先把自己的轨迹转成统一 `ToolCallEvent`,后续提取/评估/合并/索引只认这个 schema。采集 adapter 薄,核心管线只写一遍。新增一家 agent = 只写一个采集 adapter。

### 6.4 推荐落地顺序
1. **CC 跑通完整闭环**(采集+管线+MCP 注入),验证核心。
2. **接 Codex** 用其结构化 JSONL 验证统一 schema 真的跨 agent(逼出抽象漏洞)。
3. **接 Hermes** 收尾,决定与其 learning loop 的关系。

## 7. 数据 Schema(草案)

### 7.1 统一 Trace 事件 `ToolCallEvent`
```json
{
  "event_id": "uuid",
  "session_id": "string",
  "project_id": "string",
  "host_agent": "claude-code | codex | hermes",
  "timestamp": "ISO8601",
  "kind": "tool_call | generated_code | prompt",
  "name": "string",
  "input": { "schema": "...", "sample": "..." },
  "output": { "sample": "...", "status": "success | error" },
  "code_ref": "生成代码的内容或指针",
  "context_hash": "用于跨会话识别同一行为"
}
```

### 7.2 技能 Manifest(渐进式分层)
```yaml
# --- L1 元数据层(召回时仅注入这层)---
name: to-markdown
description: 把多种来源(doc/pdf/含图文本)转换为 markdown
when_to_use: 用户需要把非 md 文档统一为 markdown 时
signature:
  input: { source: path, type: "auto|doc|pdf|text" }
  output: markdown_string
tags: [convert, markdown, document]

# --- L2 正文层(模型决定展开后加载)---
implementation_ref: ./impl.py
dependencies: [...]
host_native:
  mcp_tool: to_markdown
  skill_md: ./SKILL.md

# --- L3 资源层(执行时加载)---
test_samples:
  - { input: {...}, expected_output_hash: "..." }
fixtures: [...]

# --- L4 治理/血缘层(合并/审查时加载)---
lineage:
  merged_from: [doc2md@v1, pdf2md@v1, imgtext2md@v1]
  snapshot_refs: [...]
quality:
  uses: 42
  success_rate: 0.95
  last_used: "..."
iteration_log: [...]
source: { author, team_visibility: "private|team", origin_host }
```

> 渐进披露:召回只读 L1;展开读 L2;执行读 L3;合并/审查读 L4。各阶段不加载无关层(例:合并时不需要唤起标准/L1 的 when_to_use)。

## 8. 团队共享池

- **形态**:本地库为主,定期向远程池**推送**自己转正的技能、**拉取**他人技能并走同一套合并管线。
- **核心难点不是技术是治理与安全**(自动调用他人可执行代码 = 供应链风险):
  - **沙箱执行**替代人工读码审查。
  - **来源签名 + 权限 + 可见性**(private / team)。
  - **命名冲突**:用血缘 + 命名空间消解。
  - **质量参差**:用运行时成功率排序与门禁。
- **定位**:放到最后阶段。MVP 先做单人本地库,闭环验证后再开团队池。

## 9. 困难点与缓解(诚实清单)

| # | 难点 | 限定程序类后能否自动 | 缓解 |
|---|---|---|---|
| ① | 该不该沉淀 | ✅ 基本全自动 | 复用频次 + 测试跑通,而非语义判断 |
| ② | 最小单元粒度 | ⚠️ 大部分自动 | AST/纯度/共享度判定;边界进异步人审 |
| ③ | 递归合并语义漂移 | ⚠️ 大部分自动 | 测试集并集门禁 + 保守阈值 + 可回退 + 异步抽查 |
| ④ | 召回唤起精度 | ✅ 自动 | 渐进披露 + 具体触发器 + 保守阈值 |
| ⑤ | 团队池安全 | 🔴 判断可自动,安全需工程 | 沙箱 + 签名 + 权限,放最后阶段 |

> 结论:限定程序类后,**人审从"每个工具入库阻塞门"降级为"粒度边界 + 合并抽查"的异步兜底,关键路径无人审**。代价是放弃提示词类的自动沉淀(无二元反馈)。

## 10. 分阶段路线图

### MVP(数周,单人)
- 宿主:**仅 Claude Code**。
- 范围:**仅可执行"格式转 md"类工具**。
- 入库:基于复用频次(≥3)+ 测试跑通的自动门禁。
- 合并:简单语义聚类 + 测试集并集判据,人审兜底。
- 服务:本地 MCP server 注入。
- 目标:跑通"采集→评估→合并→召回→迭代"完整闭环。

### 阶段二(数周)
- 接 **Codex**,用结构化 JSONL 验证统一 trace schema 的跨 agent 抽象。
- 扩展工具品类(更多程序类)。
- 完善粒度判定(最小单元拆链)。

### 阶段三(数月)
- 接 **Hermes**,决定与其 learning loop 的共存/接管。
- 开 **团队共享池**(沙箱 + 签名 + 权限 + 治理)。
- 接入官方 MCP Registry 分发。
- (可选)开始做提示词类沉淀(需引入软指标/人审)。

## 11. 复杂度与可行性结论

- **整体复杂度 7.5/10**;难度集中在 ①无感识别 与 ②最小单元粒度,限定程序类后大幅可控。
- **可行,但别一次做全**:单人 MVP 数周,完整版(含团队池)数月。
- **现成可抄的零件清晰**:容器/渐进披露抄 Claude Skills;记录/合并/评估抄 Yunjue;合并去重抄 Mem0;分发层用 MCP Registry。
- **差异化护城河**:运行时质量信号(真实成功率)——市场上所有分发型产品都缺。
